Como o Vigia.js funciona
por debaixo dos panos

Uma biblioteca de ~3.400 linhas, sem dependências além do axios, que transforma um <form> comum do Blade em um formulário que valida, aplica máscaras, envia por AJAX, entende as respostas do Laravel e coloca cada erro no campo certo. Aqui está cada engrenagem, com o porquê de cada decisão.

01O que é, em 1 minuto

A ideia central cabe em uma frase: o HTML descreve, o Vigia executa, o servidor confirma.

📝 O HTML descreve

Regras em data-rules, mensagens em data-msg-*, máscaras em data-mask. Nenhuma linha de JavaScript para o caso comum.

⚙️ O Vigia executa

Valida enquanto a pessoa digita, formata CPF e dinheiro, envia por AJAX com token e mostra o carregando.

🛡️ O servidor confirma

O Laravel valida de novo (segurança) e responde num formato fixo. O Vigia põe cada erro embaixo do campo com o mesmo name.

O problema que ele resolve: em todo formulário AJAX, alguém escreve de novo o mesmo código — pegar os campos, validar, montar o FormData, mandar o token, travar o botão, ler a resposta, descobrir qual erro é de qual campo, limpar os erros antigos, mostrar a mensagem de sucesso. O Vigia faz isso uma vez, do mesmo jeito em todas as telas.

?
Por que não usar só a validação do Laravel?

Porque a do Laravel só roda depois do envio. A do navegador avisa na hora, sem esperar o servidor — e evita mandar 500 MB de vídeo só para descobrir que o CPF estava errado. Mas a do navegador é conforto, não segurança: qualquer pessoa pode desligá-la. Por isso as duas existem, e o contrato entre elas é o formato da resposta.

Esse padrão faz o mesmo arquivo funcionar em um <script> no Blade e importado pelo Vite. Tudo o que está dentro da função é privado: só o objeto Vigia do final sai para fora. Por isso variáveis como config, RULES e MASKS não poluem a página e não colidem com outras bibliotecas.

?
Por que ES5 (var, function) e não classes?

Para rodar direto no navegador, sem build, inclusive em navegadores antigos de computadores corporativos. Não precisa de Vite, Babel ou npm para usar.

05A vida de um envio

O que acontece, em ordem, entre o clique em "Salvar" e a mensagem na tela. Se você entender esta seção, entende o Vigia.

  1. O clique vira um evento submit

    O Vigia escuta o submit do form (não o clique do botão). Assim, apertar Enter num campo também passa por ele. O _onSubmit chama event.preventDefault() para a página não recarregar e guarda event.submitter (qual botão foi clicado).

  2. Proteção contra clique duplo e confirmação

    Se this.loading já é true, o envio é ignorado. Se o form tem data-vigia-confirm="Tem certeza?", aparece o window.confirm; "Cancelar" para tudo.

  3. Validação completa no navegador

    validate() lê os dados (getData), junta as regras do HTML e do JS (rules()), roda o motor e desenha os erros. Se algo falhar: foca o primeiro campo inválido (na ordem da tela), dispara vigia:invalid e para aqui — nada vai para o servidor.

  4. vigia:before: o último ponto de parada

    Evento cancelável com os dados que serão enviados. Um e.preventDefault() ou um onBefore que devolve false cancela o envio sem erro.

  5. Montagem do corpo e trava da tela

    toFormData() monta o multipart (arquivos inclusos), acrescenta o name=value do botão clicado e _setLoading(true) põe a classe vigia-loading no form, aria-busy="true", desabilita todos os botões de envio e troca o texto do clicado pelo data-loading-text.

  6. Interceptor de ida (axios)

    Acrescenta X-Requested-With: XMLHttpRequest, Accept: application/json e X-CSRF-TOKEN. Se o método é PUT/PATCH/DELETE, troca por POST com _method. Durante o upload, onUploadProgress atualiza a barra [data-vigia-progress].

  7. O Laravel processa

    O middleware de CSRF confere o cabeçalho, o _method vira PUT, o controller valida e o ResponseService (ou o próprio Laravel, no 422) responde em JSON.

  8. Interceptor de volta: tradução

    Toda resposta vira o mesmo objeto { success, status, message, data, errors, meta, requestId, httpStatus }. Respostas 4xx/5xx, falta de rede e tempo esgotado viram um VigiaError com isValidation, isNetwork, isTimeout...

  9. Sucesso ou erro na tela

    Sucesso: limpa os erros, mostra a mensagem (verde, amarela para aviso, azul para info), dispara vigia:success, aplica reset e redirect se configurados. Erro: cada mensagem vai para o seu campo; o que não tem campo vira a mensagem geral; dispara vigia:error.

  10. Sempre: destrava e vigia:complete

    Os botões voltam ao estado e texto originais (inclusive os que já estavam desabilitados antes continuam desabilitados) e o evento vigia:complete roda em qualquer desfecho.

i
submit() nunca rejeita

A Promise de vigia.submit() sempre resolve: com a resposta, com { valid: false, errors } ou com null (cancelado). Os erros já foram mostrados na tela e nos eventos — você não precisa de try/catch.

06Inicialização

Como um form com data-vigia "ganha vida" sem nenhuma chamada sua.

  1. Quando o arquivo carrega

    Se a página ainda está sendo lida (document.readyState === 'loading'), espera o DOMContentLoaded. Se já terminou, agenda com setTimeout(start, 0) — dá tempo de você chamar Vigia.config({ autoInit: false }) logo depois do <script>.

  2. init(document) varre a página

    Primeiro aplica as máscaras de todo [data-mask] (estando ou não dentro de um form Vigia). Depois cria uma instância para cada form[data-vigia] ou [data-vigia-form].

  3. MutationObserver vigia o que chega depois

    Todo elemento adicionado à página (modal carregado por AJAX, linha nova de tabela, componente do Livewire) passa por init(node). Por isso um form que aparece depois também funciona sozinho.

Uma instância por form, sempre a mesma

formFor (simplificado)
function formFor(el, options) {
    if (el.__vigia) {                       // já existe?
        if (options) el.__vigia.configure(options);
        return el.__vigia;                  // devolve a mesma
    }
    el.__vigia = new VigiaForm(el, options);
    return el.__vigia;
}

A instância fica guardada no próprio elemento (form.__vigia). Chamar Vigia.form(form, {...}) num form que o auto-init já criou não cria outra: só acrescenta as opções. Por isso dá para ter data-vigia no HTML e ainda assim chamar Vigia.form(form, { rules: {...} }) no script.

O que o construtor faz

  • configure(options) — junta as opções (ver próxima seção).
  • _bind() — liga form.noValidate = true (desliga os balões nativos do navegador, para o Vigia mostrar as mensagens dele) e registra 4 ouvintes no form: submit, focusout, input, change.
  • Lê data-vigia-errors: se o form já nasce com erros (JSON), mostra na hora. Útil quando a página volta de um envio tradicional.
?
Por que os ouvintes ficam no form e não em cada campo?

Delegação de eventos: input, change e focusout sobem do campo até o form. Com 4 ouvintes no form, campos adicionados depois (um item novo de uma lista) já funcionam, sem registrar nada. E focusout é usado no lugar de blur justamente porque blur não sobe.

Para remover: vigia.destroy() tira os ouvintes, limpa os erros e apaga form.__vigia. Use antes de remover um form da página em uma tela de página única.

07Configuração e prioridade

Há três lugares para configurar. Quando dois dizem coisas diferentes, vale o mais específico.

1Opções do JS — Vigia.form(form, { validateOn: 'submit' })
2JSON do data-vigia — data-vigia='{"validateOn":"submit"}'
3Atributo data-vigia-* — data-vigia-validate-on="submit"
4Configuração global — Vigia.config({ validateOn: 'submit' })

Por dentro, configure() faz extend({}, this.options, jsonDoDataVigia, opcoesDoJs) — o último ganha. Depois, cada leitura passa por option(nome, atributo, padrão), que procura nessa ordem: this.options → atributo data-vigia-* → padrão global.

rules, messages e labels são somados, não substituídos: os do data-vigia, os de data-vigia-rules/-messages/-labels e os do JS se juntam.

08Dos campos aos dados

Como o Vigia transforma os <input> em um objeto para validar e em um FormData para enviar.

Quais campos entram (isSubmittable)

Um campo entra se tem name, não está disabled e não é botão (button, submit, reset, image). Checkbox e radio só entram se marcados. É exatamente a regra do envio nativo do HTML.

✓
Truque: disabled desliga a validação também

Campo disabled não é validado nem enviado. Para um campo que só vale em certa situação (ex.: "descreva a sucessão" só quando a opção está marcada), desabilite-o quando não se aplica — nenhuma regra extra é necessária.

Dois formatos de saída

getData() para validar

Objeto aninhado. As regras leem dele com caminhos como itens.0.nome (getNested), e regras como same:senha consultam outros campos.

toFormData() para enviar

Multipart com os name originais, um append por arquivo, por item de lista e por opção. É o que o $request->input() e o $request->file() leem.

09Motor de validação

O coração do Vigia. Funciona sem DOM — Vigia.validate(dados, regras) roda até no Node.

De onde vêm as regras de um campo

VigiaForm.rules() monta um objeto { chave: [regras] } juntando três fontes. Se a mesma regra aparece em duas, vale a primeira:

  1. Regras do JS — options.rules / data-vigia-rules, que aceitam curinga: 'itens.*.quantidade'.
  2. data-rules do campo.
  3. Atributos nativos do HTML, traduzidos:
Atributo HTMLVira a regra
requiredrequired
type="email" / url / number / date / timeemail / url / numeric / date / time
type="datetime-local"datetime:Y-m-d\TH:i (ou com segundos, se step < 60)
minlength="3"min_length:3
maxlength="150"max_length:150 — ignorado se o campo tem máscara (os pontos e traços contariam)
min / max (em number e range)min:N / max:N
pattern="[A-Z]{3}"regex:/^(?:[A-Z]{3})$/u

Os quatro formatos de regra (parseRules)

todos equivalentes onde fizer sentido
'required|email|max_length:150'                 // texto, igual ao PHP
['required', 'integer', 'min:1']               // lista
{ required: true, in: ['a', 'b'] }             // objeto
['required', function (valor, dados, campo) {   // lista com função
    return valor !== 'admin' || 'Esse nome é reservado.';
}]

Um detalhe esperto do texto: regex é sempre lido por último. Tudo depois de regex: vira o padrão, inteiro — assim um | dentro da expressão (regex:/^(a|b)$/) não é confundido com o separador de regras. Por isso coloque regex no fim.

Curingas: itens.*.quantidade (expandRules)

Antes de validar, cada regra com * é multiplicada pelos itens que existem nos dados. Com dois itens na tela, itens.*.quantidade vira itens.0.quantidade e itens.1.quantidade. Se a pessoa adicionar um terceiro, a próxima validação já inclui itens.2. É o mesmo comportamento do Laravel.

Como um campo é validado (validateField)

  1. Pega o valor pelo caminho

    getNested(dados, 'itens.1.quantidade') e decide se está vazio (valueExists): null, texto só com espaços, lista vazia e objeto vazio contam como vazio.

  2. Campo vazio? Só regras de presença

    Com o campo vazio, só rodam required, required_if, required_with e accepted. Um email num campo opcional vazio não reclama — igual ao Laravel com nullable. nullable em si é ignorado.

  3. As regras rodam em sequência, em cadeia de Promises

    Uma depois da outra, na ordem declarada. Todas rodam (não para no primeiro erro); firstErrorOnly decide quantas mensagens aparecem.

  4. Cada regra passa por runRule

    Função própria? Roda. Regra só de servidor (unique, exists, callback)? Passa. Valor é lista/objeto e a regra espera texto (email, cpf...)? Falha. Regra desconhecida? Passa (igual ao ValidationHelper) — um erro de digitação em data-rules não trava o form.

O que uma regra pode devolver

RetornoSignificado
true (ou qualquer valor "verdadeiro")Válido.
falseInválido, com a mensagem padrão da regra.
'Texto'Inválido com esse texto. :field vira o rótulo do campo.
'' (texto vazio)Inválido com a mensagem padrão.

!
Regra-função não roda com campo vazio

Consequência direta do passo 2. Para regras do tipo "preencha A ou B", ponha a função num campo oculto que sempre tem valor (a "âncora") e mostre o erro com data-error-for. Veja a receita.

Campos são validados em paralelo

validate() roda todos os campos ao mesmo tempo (Promise.all) e depois reordena os erros na ordem em que as regras foram declaradas — e o VigiaForm reordena de novo pela posição na tela (_inDomOrder). Por isso o "primeiro erro" focado é sempre o mais acima na página, mesmo que uma regra assíncrona termine antes.

Regras que você cria (Vigia.rules.add)

regra global, usável em qualquer data-rules
Vigia.rules.add('maior_idade', function (valor) {
    var nascimento = Vigia.utils.parseDate(valor, 'd/m/Y');
    if (!nascimento) return false;
    var limite = new Date();
    limite.setFullYear(limite.getFullYear() - 18);
    return nascimento <= limite;
}, 'É preciso ter 18 anos ou mais.');

// <input name="nascimento" data-mask="date" data-rules="required|date_br|maior_idade">

A assinatura de uma regra global é (valor, parametros, contexto), onde contexto = { data, field, options }. Os parâmetros vêm do texto: minha_regra:10,20 → ['10', '20'].

10Mensagens e rótulos

Como o Vigia escolhe a frase de cada erro e o nome do campo dentro dela.

A escada da mensagem (messageFor)

Para o campo itens.1.quantidade e a regra max, a primeira que existir vence:

3messages['max'] — para a regra em todo o form
4Atributo data-msg-max no campo (_ vira -: min_length → data-msg-min-length)
5Vigia.config({ messages: { max: '...' } }) — global

7Mensagem padrão em português (MESSAGES)

11Validação ao vivo

O que dispara a validação enquanto a pessoa preenche, e como o Vigia evita respostas fora de ordem.

Checkbox, radio, select e arquivo validam no change, em qualquer modo — não faz sentido esperar a pessoa "sair" de um checkbox.

?
Por que blur é o padrão?

Validar a cada tecla grita "e-mail inválido" na 1ª letra. Validar só no envio deixa a pessoa errar tudo antes de saber. O blur espera a pessoa terminar o campo e, depois que existe um erro, passa a conferir a cada tecla — o erro some no instante em que é corrigido.

Proteção contra corrida (_sequence)

Regras assíncronas (como remote, que pergunta ao servidor) podem terminar fora de ordem: a pessoa digita "ana", depois "ana@x.com", e a resposta do "ana" chega por último. Para isso não sobrescrever o resultado novo:

validateField (resumo)
var sequence = (this._sequence[key] || 0) + 1;
this._sequence[key] = sequence;

return validate(...).then(function (result) {
    if (self._sequence[key] !== sequence) {
        return result;          // chegou uma validação mais nova: ignora esta
    }
    // ... desenha os erros
});

Campos que dependem de outros (_revalidateDependents)

Quando um campo muda, o Vigia procura campos que já estão com erro e cujas regras citam esse campo como parâmetro (same:senha, required_if:tipo,pj, after:data_inicio) ou são a confirmação dele (senha ↔ senha_confirmation). Esses são validados de novo. Resultado: corrigir a senha apaga o erro "a confirmação não confere" sem a pessoa tocar na confirmação.

12Exibição dos erros

Onde cada mensagem aparece, com que classes, e o que acontece com erros que não têm campo.

Onde a mensagem do campo aparece (_feedbackFor)

  1. Um elemento seu com data-error-for="chave" (aceita itens.0.nome ou itens[0][nome]). Use para grupos de checkbox e para a "âncora".
  2. Um que o Vigia já criou antes para essa chave (data-vigia-feedback-for).
  3. Cria um <div> logo depois do campo, com id="vigia-erro-N", aria-live="polite" e as classes invalid-feedback vigia-feedback. Ajustes: em checkbox/radio, vai depois do .form-check/label; em .input-group, depois do grupo (para não quebrar o visual do Bootstrap).

O que muda no campo

  • Classes is-invalid invalid vigia-invalid.
  • aria-invalid="true" e o id da mensagem em aria-describedby — o leitor de tela lê o erro ao focar o campo.
  • Quando corrige: tudo é removido, e a <div> criada pelo Vigia é apagada (a sua, de data-error-for, só é escondida).

Erros sem campo na tela

showErrors() separa os erros em dois grupos. Chaves que começam com _ (_general, _system) ou que não acham nenhum campo nem data-error-for são "órfãs" e viram a mensagem geral. Um erro nunca some em silêncio.

A mensagem geral (notify)

  • Vai no [data-vigia-message] do form. Se não existir, o Vigia cria um no topo do form.
  • Recebe role="alert" para erro (o leitor de tela anuncia na hora) e role="status" para o resto.
  • Classes por tipo: success, error, warning (status aviso), info.
✓
Seguro contra injeção de HTML

Toda mensagem — da regra ou do servidor — é escrita com textContent / createTextNode, nunca innerHTML. Se um nome de usuário malicioso voltar dentro de uma mensagem de erro, ele aparece como texto, não roda como código.

A lógica da mensagem geral num erro do servidor

Quando o envio falha, o Vigia evita repetir o óbvio:

  • Há erros órfãos → a mensagem geral mostra só eles.
  • Todos os erros acharam campo → nenhuma mensagem geral (os campos já explicam).
  • Não veio nenhum erro de campo (403, 500, sem rede) → a mensagem geral mostra a mensagem da resposta ou a mensagem HTTP padrão.

13Máscaras

Um mini-motor de formatação que roda a cada tecla, sem perder a posição do cursor.

A linguagem dos padrões

9

Um dígito.

a

Uma letra (A–Z).

*

Letra ou dígito. O resto é literal: . - / ( ) espaço.

Como applyPattern formata

  1. Limpa

    Tira tudo que não é letra ou dígito: "123.45" → "12345".

  2. Percorre o padrão

    Literal? Escreve. Marcador? Pega o próximo caractere digitado que ele aceita (pulando os que não aceita: uma letra num marcador 9 é descartada).

  3. Corta literais soltos no fim

    "123." vira "123" — senão apagar com Backspace esbarraria no ponto e não sairia do lugar.

Máscaras que mudam de forma

Um padrão pode ser uma função que recebe o que foi digitado e devolve o padrão. É assim que telefone alterna entre fixo e celular, e cpf_cnpj entre CPF e CNPJ:

MASKS (trecho)
cpf_cnpj: function (raw) {
    // Até 11 dígitos aceita um a mais, para a pessoa conseguir "passar" para CNPJ.
    return onlyDigits(raw).length <= 11 ? '999.999.999-999' : '99.999.999/9999-99';
},
phone: function (raw) {
    return onlyDigits(raw).length <= 10 ? '(99) 9999-99999' : '(99) 99999-9999';
}

Máscaras de número (estilo caixa registradora)

money, decimal, integer e percent não usam padrão: os dígitos entram pela direita. Digitar 1 2 3 mostra R$ 0,01 → R$ 0,12 → R$ 1,23. Um valor vindo do banco com ponto ("1234.5") é respeitado como decimal e vira R$ 1.234,50.

Ajustes por atributo: data-mask-decimals, data-mask-prefix (ex.: "" para tirar o "R$ "), data-mask-suffix, data-mask-thousands, data-mask-negative.

O cursor no lugar certo

Reformatar o valor faria o cursor pular para o fim — impossível corrigir um dígito no meio do CPF. O onMaskInput resolve contando quantos caracteres reais (não literais) existem antes do cursor, formata, e põe o cursor logo depois do mesmo número de caracteres reais no texto novo (caretAfterRaw).

?
Por que o ouvinte da máscara usa capture?

addEventListener('input', onMaskInput, true) roda na fase de captura, antes dos outros ouvintes. Assim o x-model do Alpine, o Livewire ou o seu código já recebem o valor formatado. E durante a digitação com teclado de composição (acentos em celulares, IME), a máscara espera a composição terminar (event.isComposing).

Outros cuidados automáticos

  • inputmode: se o campo não tem, o Vigia põe numeric ou decimal em máscaras só de números — o celular abre o teclado numérico.
  • Valor inicial: se o campo já vem preenchido (edição), é formatado na inicialização.
  • Sem máscara no envio: com data-unmask, o valor enviado (e validado!) é o limpo.

14Camada HTTP

Uma instância própria do axios com dois interceptores. É aqui que está a adaptação para o Laravel.

Criada só quando precisa (getAxios)

A instância é criada na primeira requisição, não quando o arquivo carrega. Duas consequências práticas:

  • O axios pode ser carregado depois do Vigia — inclusive o do resources/js/bootstrap.js do Laravel via Vite (window.axios = axios). Só precisa existir na hora do primeiro envio.
  • É criada com window.axios.create(), então os interceptores do Vigia não afetam o window.axios que o resto da aplicação usa.

Interceptor de ida

?
Por que multipart e não JSON?

Multipart é o formato do envio nativo de um form: aceita arquivos, e o Laravel lê com $request->input() e $request->file() sem configuração. JSON não leva arquivos. Com { json: true } você pode mandar JSON quando não houver arquivos — e aí o método original (PUT etc.) é mantido, porque o Laravel lê corpo JSON em qualquer método.

?
Por que _method?

O PHP só monta $_POST e $_FILES a partir de corpo multipart quando o método é POST. Um PUT multipart chegaria com os dados vazios. O Laravel tem a solução padrão — o campo _method, o mesmo do @method('PUT') do Blade — e o roteador trata a requisição como PUT.

Objetos viram campos com colchetes (objectToFormData)

// nome=A  ativo=1  nada=  tags[]=x  tags[]=y  itens[0][qtd]=2

Booleanos viram 1/0 e null vira texto vazio — que o middleware ConvertEmptyStringsToNull do Laravel transforma de volta em null.

Interceptor de volta: tudo vira o mesmo objeto

normalizeResponse aceita o envelope do ResponseService e também o formato nativo do Laravel ({ message, errors }): ele reconhece um "envelope" se a resposta tem success, mensagem ou errors.

17Estado e Alpine.js

Toda mudança passa por um só lugar, o que torna a integração com frameworks reativos trivial.

A instância guarda o estado em propriedades públicas (errors, loading, progress, response, message, messageType), e toda alteração passa por _setState(), que chama onState(estado) com uma foto completa, incluindo valid. É o mesmo padrão de "fonte única da verdade" de bibliotecas como Redux.

21Armadilhas

            
O que já confundiu alguém, e por quê.


            
"O servidor enviou uma resposta inesperada."

                
O controller devolveu HTML com status 2xx. Causas comuns: return redirect()->back() (o axios segue o redirecionamento e recebe a página), return view(...), um dd() esquecido, ou um aviso do PHP impresso antes do JSON. Responda sempre com ResponseService nas rotas que o Vigia chama.

            


            
419 "Sua sessão expirou" logo no primeiro envio

                
O Vigia não achou o token. Confira se o layout tem <meta name="csrf-token" content="{{ csrf_token() }}"> ou se o form tem @csrf. Abra a aba Rede do navegador e veja se o cabeçalho X-CSRF-TOKEN foi enviado. Vigia.http.token() no console mostra o que ele encontrou.

            


            
Os dados chegam vazios num PUT

                
Isso acontece se você usar outro cliente HTTP com multipart em PUT. O Vigia já converte para POST + _method. Se você passou { json: true } com arquivos, os arquivos não vão (JSON não carrega arquivos).

            


            
A data passa no navegador e falha no Laravel (ou o contrário)

                
Com data-mask="date", a tela mostra 31/12/2026. Sem data-unmask, é isso que vai ao servidor: use date_br no HTML e date_format:d/m/Y no Laravel. Com data-unmask, vai 2026-12-31 — e a validação do navegador também passa a ver 2026-12-31: troque para date no HTML e date no Laravel.

            


            
file_size:2M no HTML e max:2 no Laravel

                
O max do Laravel para arquivos é em kilobytes: 2 MB é max:2048. Com max:2, todo arquivo acima de 2 KB é recusado pelo servidor.

            


            
Minha regra-função não roda

                
Ela não roda com o campo vazio (só regras de presença rodam). Use a âncora oculta da receita "A ou B". Confira também se o campo não está disabled.

            


            
Checkbox desmarcado não chega no controller

                
Igual ao envio nativo: só os marcados vão. No Laravel, leia com $request->boolean('ativo'), que devolve false quando o campo não veio.

            


            
Vigia.config({ timeout }) não mudou nada

                
O timeout global é lido quando a instância do axios é criada (na 1ª requisição). Chame Vigia.config antes de qualquer envio, ou passe por formulário: data-vigia='{"request":{"timeout":0}}', que vale a cada envio.

            


            
O maxlength não valida no campo com máscara

                
De propósito: os pontos e traços da máscara contariam como caracteres. A própria máscara já limita o tamanho.

            


            
Escrevi uma regra errada e o form aceitou tudo

                
Regra desconhecida passa (para não travar o form por um erro de digitação). Teste a regra no laboratório ou com Vigia.rules.has('minha_regra').

            


            
Os campos do form ficam marcados pela validação nativa do navegador

                
Não deveriam: o Vigia liga form.noValidate = true. Se acontecer, o form não tem data-vigia (não foi inicializado) ou outra biblioteca (jQuery Validate) está ligada nele. Um form deve ter um só validador.

23Como explicar para alguém

            
Três versões da mesma explicação, para três públicos, e as perguntas que costumam vir depois.


            

                

                    
30 segundosPara gestor ou cliente

                    
"Criamos uma peça que padroniza todos os formulários do sistema. A pessoa vê o erro na hora em que digita, com a mensagem embaixo do campo certo, e os dados são conferidos de novo no servidor por segurança. Cada tela nova sai mais rápido e todas se comportam igual."

                

                

                    
2 minutosPara um dev que vai usar

                    
"Põe data-vigia no form, as regras em data-rules e as máscaras em data-mask. Ele valida no navegador, envia em AJAX com o token do Laravel e entende a resposta do ResponseService: cada chave de errors vai para o campo com o mesmo name. Se precisa reagir, escuta vigia:success. No controller, valida de novo com $request->validate() e responde com ResponseService."

                

                

                    
10 minutosPara um dev sênior que vai revisar

                    
"É um módulo UMD em ES5, sem build. Tem três motores sem DOM — regras (62, assíncronas, com curinga), mensagens (escada de prioridade, rótulos com '(item N)') e máscaras (padrões 9/a/*, padrões dinâmicos, números à direita, cursor preservado). Em cima, um VigiaForm por form, com eventos delegados, estado centralizado em _setState e proteção de corrida por campo. A rede é uma instância própria do axios, criada sob demanda, com um interceptor que põe o X-CSRF-TOKEN e converte PUT/PATCH/DELETE em POST + _method, e outro que normaliza qualquer resposta num objeto só. Mensagens são escritas com textContent; erros sem campo nunca somem."

                

            


            
Perguntas que vão aparecer


            
"Por que não usar uma biblioteca pronta (jQuery Validate, VeeValidate, Livewire)?"

                
O jQuery Validate só valida: o envio, o token, a leitura da resposta e o mapeamento dos erros do servidor ficam por conta de cada tela. O VeeValidate exige Vue. O Livewire exige reescrever a tela como componente. O Vigia funciona num Blade comum, fala o mesmo formato do backend e cobre o ciclo inteiro — e as regras brasileiras (CPF, CNPJ, PIS, CNH, placa) já vêm prontas.

            


            
"Se o navegador valida, por que validar de novo no servidor?"

                
Porque qualquer pessoa pode desligar o JavaScript ou mandar a requisição direto com outra ferramenta. A validação do navegador é para a experiência; a do servidor é para a segurança e a integridade dos dados. Regras como unique só o servidor pode conferir.

            


            
"Como um erro do servidor sabe em qual campo aparecer?"

                
A chave do erro é o nome do campo em notação de pontos (itens.1.quantidade), que é exatamente o que o Laravel produz. O Vigia converte para colchetes (itens[1][quantidade]), procura o campo com esse name e, se não achar, sobe um nível. O que não acha campo vira a mensagem geral.

            


            
"E se a pessoa clicar duas vezes em Salvar?"

                
Durante o envio, loading é true e todos os botões de envio ficam desabilitados; um segundo submit é ignorado logo na primeira linha de submit().

            


            
"É seguro? E o CSRF?"

                
O token vai no cabeçalho X-CSRF-TOKEN, conferido pelo middleware do Laravel. Mensagens nunca são inseridas como HTML. Só há envio ao seu próprio backend (e às rotas que você puser em remote:).

            


            
"E a acessibilidade?"

                
Campo inválido recebe aria-invalid e aria-describedby apontando para a mensagem; as mensagens têm aria-live; a mensagem geral de erro usa role="alert"; o form em envio recebe aria-busy; o foco vai para o primeiro erro.

            


            
"Funciona com conteúdo carregado depois (modal, Livewire, Turbo)?"

                
Sim. Um MutationObserver inicializa forms e máscaras que entram na página; os ouvintes são delegados ao form, então campos novos já funcionam.

            


            
"Qual o custo de desempenho?"

                
Quatro ouvintes por form, independentemente do número de campos. A validação ao vivo valida só o campo alterado (e os que dependem dele). O axios só é instanciado no primeiro envio.
