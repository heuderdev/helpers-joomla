Vigia.js

Validação no navegador, máscaras e requisições com axios para componentes Joomla, falando a mesma língua do ValidationHelper e do ApiResponseHelper.

Visão geral

O Vigia.js é um micro framework JavaScript (um arquivo, sem build) que cuida do formulário de ponta a ponta:

  • Valida no navegador com as mesmas regras e mensagens do ValidationHelper: required|cpf|max_length:150 funciona igual nos dois lados.
  • Mostra os erros do servidor no campo certo: a resposta 422 do ApiResponseHelper::fromValidation() aparece embaixo de cada campo, inclusive itens.1.quantidade → itens[1][quantidade].
  • Máscaras brasileiras: CPF, CNPJ, CPF/CNPJ, telefone, CEP, data, hora, dinheiro, placa, cartão, PIS e padrões próprios.
  • Requisições com axios: token CSRF do Joomla automático, resposta normalizada e erros padronizados.
  • Alpine.js opcional: x-data="vigia" com erros reativos e x-mask.
Regras no PHPValidationHelper::clientConfig()
↓
NavegadorVigia.js valida enquanto a pessoa digita
↓
ServidorValidationHelper valida de novo (inclusive unique/exists)
↓
Resposta 422ApiResponseHelper::fromValidation() → Vigia mostra no campo

A validação no navegador é conforto, não segurança: qualquer um pode desligar o JavaScript ou chamar a URL direto. O controller sempre valida com o ValidationHelper.

Instalação

Copie js/vigia.js e js/vigia.css do repositório para a pasta de mídia do componente (ex.: media/com_loja/js/) e carregue o axios antes do Vigia. O CSS é opcional com Bootstrap (Joomla 4/5 e a maioria dos templates).

HTML
<script src="https://cdnjs.cloudflare.com/ajax/libs/axios/1.7.7/axios.min.js"></script>
<script src="/media/com_loja/js/vigia.js"></script>
<link rel="stylesheet" href="/media/com_loja/js/vigia.css">

<!-- Opcional, depois do Vigia -->
<script defer src="https://cdn.jsdelivr.net/npm/alpinejs@3.14.1/dist/cdn.min.js"></script>
Joomla
// Na view do Joomla (3, 4 e 5)
JHtml::_('script', 'https://cdnjs.cloudflare.com/ajax/libs/axios/1.7.7/axios.min.js');
JHtml::_('script', 'com_loja/vigia.js', array('relative' => true, 'version' => 'auto'));
JHtml::_('stylesheet', 'com_loja/vigia.css', array('relative' => true, 'version' => 'auto'));

Não há init() para chamar: ao carregar a página, o Vigia ativa todo <form data-vigia> e todo campo com data-mask, inclusive os adicionados depois (linhas de itens criadas por JavaScript).

Para ver tudo funcionando sem Joomla, abra js/exemplo.html do repositório no navegador: um servidor falso responde como o ApiResponseHelper. O exemplo completo de controller e view está em exemplos/ComoUsarVigia.php.

controller.php
public function salvar()
{
    try {
        if (!JSession::checkToken()) {
            return ApiResponseHelper::forbidden('Sua sessão expirou. Recarregue a página.');
        }

        $dados = InputHelper::post(array('nome' => 'string', 'email' => 'string', 'cpf' => 'string'));

        $validacao = ValidationHelper::validate($dados, array(
            'nome' => 'required|min_length:3',
            'email' => 'required|email',
            'cpf' => 'required|cpf',
        ));

        if (!$validacao['valid']) {
            return ApiResponseHelper::fromValidation($validacao);   // 422: o Vigia mostra nos campos
        }

        // ... grava

        return ApiResponseHelper::created('Cliente cadastrado com sucesso.', array('id' => $id));
    } catch (Throwable $e) {
        return ApiResponseHelper::exception($e);
    }
}

O que acontece:

  1. Ao sair de um campo, ele é validado; depois do primeiro erro, a mensagem se atualiza a cada tecla.
  2. No envio, tudo é validado. Com erro, nada é enviado e o foco vai para o primeiro campo inválido.
  3. Sem erro, o formulário é enviado pelo axios (multipart, com o token), o botão fica desabilitado com "Salvando…".
  4. Resposta 422: cada mensagem aparece embaixo do seu campo. Resposta de sucesso: a mensagem aparece em [data-vigia-message].

Regras

Declare em data-rules com a mesma sintaxe do ValidationHelper: regras separadas por |, parâmetros depois de :, separados por vírgula; regex sempre por último. Com o campo vazio, só as regras de presença (required, required_if, required_with, accepted) rodam: um campo opcional vazio não é "e-mail inválido".

Regras no JavaScript

Vigia.form('#pedido', {
    rules: {
        'cliente_id': 'required|integer',
        'itens.*.produto': 'required|min_length:2',          // cada item: itens[0][produto], itens[1][produto]...
        'itens.*.quantidade': ['required', 'integer', 'min:1'],
        'status': { in: ['aberto', 'pago'] },
        'cupom': [function (valor, dados, campo) {
            return valor === '' || /^[A-Z0-9]{6}$/.test(valor) || 'O cupom :field deve ter 6 letras ou números.';
        }]
    }
});

As regras do JavaScript, as do data-vigia (PHP) e as dos atributos são somadas. Uma função recebe (valor, dados, campo) e devolve true, false (mensagem padrão), uma mensagem própria ou uma Promise de um desses.

Regras declaradas uma vez, no PHP

ValidationHelper::clientConfig() transforma as regras, mensagens e rótulos do PHP no formato do Vigia. O controller e a view usam a mesma fonte, e uma mudança de regra vale nos dois lados.

class ClienteRegras
{
    public static function regras()
    {
        return array(
            'nome' => 'required|min_length:3|max_length:80',
            'email' => array('required', 'email', 'unique' => function ($valor) { /* consulta */ }),
            'documento' => 'required|cpf_cnpj',
            'itens.*.quantidade' => 'required|integer|min:1',
        );
    }
}

// controller
$validacao = ValidationHelper::validate($dados, ClienteRegras::regras(), $mensagens, $rotulos);

// view
$vigia = ValidationHelper::clientConfig(ClienteRegras::regras(), $mensagens, $rotulos);
<form data-vigia='<?php echo htmlspecialchars(json_encode($vigia), ENT_QUOTES, 'UTF-8'); ?>'
      action="<?php echo JRoute::_('index.php?option=com_loja&task=cliente.salvar&format=json'); ?>" method="post">

Ficam de fora as regras com closure e as que só o servidor confere (unique, exists, callback); o servidor continua validando tudo no envio. O resultado tem a forma {"rules": {...}, "messages": {...}, "labels": {...}}; também dá para passar cada parte em data-vigia-rules, data-vigia-messages e data-vigia-labels.

Use aspas simples no atributo e htmlspecialchars(..., ENT_QUOTES): o JSON tem aspas duplas e pode ter <, & e apóstrofos nas mensagens.

Mensagens e rótulos

As mensagens são as mesmas do ValidationHelper (O campo :field é obrigatório.), com :field, :value, :min, :max, :other e :date. O nome no lugar de :field vem, nesta ordem:

  1. dos rótulos do PHP/JS (labels, inclusive itens.*.quantidade);
  2. do atributo data-label do campo;
  3. do texto do <label for> (sem a estrela * do Joomla) ou do <label> em volta;
  4. do nome do campo, como no PHP: data_nascimento → "Data nascimento".

Campos de lista ganham o número do item: itens.1.quantidade → "Quantidade (item 2)".

<!-- Mensagem própria de uma regra, direto no campo -->
<input name="termos" type="checkbox" data-rules="accepted" data-msg-accepted="Você precisa aceitar os termos.">
Vigia.form('#cadastro', {
    messages: {
        'email.required': 'Informe seu e-mail.',          // campo + regra
        'itens.*.quantidade.min': 'Quantidade mínima: :value.',
        'required': 'Preencha :field.'                     // regra, para o formulário todo
    },
    labels: { 'documento': 'CPF ou CNPJ' }
});

// Para o site todo
Vigia.config({ messages: { required: 'Preencha o campo :field.' } });

O campo recebe is-invalid (Bootstrap 4/5), invalid (Joomla 3) e vigia-invalid, além de aria-invalid="true" e aria-describedby apontando para a mensagem. A mensagem é criada logo depois do campo (ou depois do .input-group), com invalid-feedback vigia-feedback. Quando a pessoa corrige o campo, o erro do servidor some.

<!-- Mensagem num lugar específico -->
<input name="cidade">
<small data-error-for="cidade" class="text-danger"></small>

Mensagem geral

Mensagens de sucesso e erros sem campo aparecem, nesta ordem, em:

  1. [data-vigia-message] dentro do formulário (com alert alert-success, alert alert-danger alert-error…);
  2. Joomla.renderMessages(), se existir na página (a área de mensagens padrão do Joomla);
  3. uma caixa criada no topo do formulário.

Com erros nos campos, a mensagem geral não repete o que já está nos campos.

Padrão próprio: 9 = dígito, a = letra, * = letra ou dígito; o resto é literal ((99) 9999-9999, aaa-9999). Máscaras numéricas aceitam data-mask-decimals, data-mask-prefix, data-mask-suffix, data-mask-thousands e data-mask-negative. O campo recebe inputmode numérico/decimal (teclado certo no celular), e o cursor fica no lugar ao editar no meio.

data-unmask envia o valor sem máscara: dígitos (12345678909), número com ponto (1234.56, que o InputHelper::decimal() entende) e data dd/mm/aaaa → aaaa-mm-dd (o formato do InputHelper::date()). Sem ele, o valor vai como está na tela: as regras cpf, decimal e date_br do PHP aceitam o valor mascarado.

Vigia.mask(document.querySelector('#cpf'), 'cpf');                  // aplica em um campo
Vigia.mask.format('11222333000181', 'cnpj');                        // '11.222.333/0001-81'
Vigia.mask.unmask('R$ 1.234,56', 'money');                          // '1234.56'
Vigia.mask.add('processo', '9999999-99.9999.9.99.9999');            // máscara nova com nome

Requisições: Vigia.http

Um axios já configurado para o Joomla: manda X-Requested-With (o ApiResponseHelper responde JSON), o token CSRF no corpo (Joomla 3) e no cabeçalho X-CSRF-Token (Joomla 4/5), e converte objetos em multipart/form-data com nomes que o PHP entende (itens[0][sku]).

// Sucesso (2xx): resposta normalizada
const r = await Vigia.http.post('index.php?option=com_loja&task=pedido.salvar&format=json', {
    cliente_id: 7,
    itens: [{ sku: 'A1', qtd: 2 }],
    anexo: arquivo            // File: vai como upload
});

r.success;     // true
r.message;     // 'Pedido criado.' (o campo mensagem do ApiResponseHelper)
r.data;        // { id: 15 }
r.meta;        // { paginacao: {...} } em ApiResponseHelper::paginated()
r.httpStatus;  // 201
r.requestId;   // para procurar no log do servidor

// Erro (4xx/5xx, rede, timeout): rejeita com VigiaError
try {
    await Vigia.http.delete('index.php?option=com_loja&task=pedido.excluir&id=15&format=json');
} catch (e) {
    e.message;       // mensagem do servidor ou uma padrão em português
    e.httpStatus;    // 403, 404, 422, 500... (0 sem conexão)
    e.errors;        // { campo: [mensagens] }
    e.isValidation;  // 422
    e.isNetwork; e.isTimeout; e.isCancel;
}

Vigia.http.get(url, { pagina: 2 });                  // query string
Vigia.http.post(url, dados, { json: true });         // corpo JSON (o InputHelper lê; JSession::checkToken do Joomla 3 não)
Vigia.http.post(url, dados, { onUploadProgress: e => console.log(e.loaded / e.total) });
Vigia.http.instance();                               // a instância do axios (interceptors, defaults)

Quando a resposta é do ApiResponseHelper, vale a mensagem dela. Para trocar as padrões: Vigia.config({ httpMessages: { 401: '...' } }).

No controller, responda o token inválido com ApiResponseHelper::forbidden(...), não com jexit(): o jexit devolve texto com HTTP 200, e o Vigia só consegue dizer "resposta inesperada".

form.addEventListener('vigia:complete', e => {});                                  // sempre, no fim

Métodos da instância

const vigia = Vigia.form('#cadastro', { /* opções */ });   // a mesma instância do data-vigia

await vigia.validateField('email');
await vigia.submit();            // valida e envia; resolve com a resposta (nunca rejeita)

vigia.reset();
vigia.destroy();

Alpine.js

Com o Alpine na página (carregado depois do Vigia), o componente vigia e a diretiva x-mask ficam disponíveis. Os erros, o carregamento e a mensagem viram estado reativo.

<form x-data="vigia({ rules: { email: 'required|email', cpf: 'required|cpf' }, render: false }, { assinatura: null })"
      @vigia:success="assinatura = $event.detail.data"
      action="index.php?option=com_loja&task=newsletter.assinar&format=json" method="post">

    <input name="email" class="form-control" :class="{ 'is-invalid': hasError('email') }">
    <div class="invalid-feedback" x-text="error('email')"></div>

    <input name="cpf" class="form-control" x-mask:cpf :class="{ 'is-invalid': hasError('cpf') }">
    <div class="invalid-feedback" x-text="error('cpf')"></div>

    <button :disabled="loading" x-text="loading ? 'Enviando…' : 'Assinar'"></button>
    <p x-show="message" x-text="message"></p>
    <progress x-show="loading" :value="progress" max="100"></progress>

    <?php echo JHtml::_('form.token'); ?>
</form>

hasError('campo')true/false

x-mask="'cpf'" (expressão) ou x-mask:cpf (modificador) aplicam máscara e funcionam com x-model: o modelo recebe o valor já mascarado. Não use @submit.prevent no formulário: o Vigia já cuida do envio.

Formulários clássicos do Joomla

Para formulários que recarregam a página (task save com redirect), use data-vigia-submit="native": o Vigia valida e, se estiver tudo certo, deixa o navegador enviar.

<form data-vigia data-vigia-submit="native" action="<?php echo JRoute::_('index.php?option=com_loja'); ?>" method="post"
      data-vigia-errors='<?php echo htmlspecialchars(json_encode($this->erros ?: new stdClass), ENT_QUOTES, 'UTF-8'); ?>'>

data-vigia-errors mostra, ao carregar, os erros que o controller guardou (por exemplo, na sessão) antes do redirect. Na barra de ferramentas do administrador, que envia com Joomla.submitbutton, valide antes:

Joomla.submitbutton = function (task) {
    const form = document.getElementById('adminForm');

    if (task === 'item.cancel') {
        return Joomla.submitform(task, form);
    }

    Vigia.form(form).validate().then(function (r) {
        if (r.valid) {
            Joomla.submitform(task, form);
        }
    });
};

Configuração global

Vigia.config({
    token: '',                    // vazio: descobre sozinho (Joomla.getOptions('csrf.token'), campo do form.token, <meta name="csrf-token">)
    timeout: 30000,
    validateOn: 'blur',
    firstErrorOnly: true,         // false mostra todas as mensagens do campo
    notify: 'auto',
    autoInit: true,               // false: chame Vigia.init() você mesmo
    classes: {
        invalid: 'is-invalid invalid vigia-invalid',
        valid: '',                // ex.: 'is-valid'
        feedback: 'invalid-feedback vigia-feedback',
        loading: 'vigia-loading',
        alert: { success: 'alert alert-success', error: 'alert alert-danger alert-error', warning: 'alert alert-warning', info: 'alert alert-info' }
    },
    messages: {},                 // troca mensagens padrão
    httpMessages: {}              // troca mensagens de erro HTTP
});

Regras e máscaras próprias

// Regra síncrona
Vigia.rules.add('par', function (valor) {
    return parseInt(valor, 10) % 2 === 0;
}, 'O campo :field deve ser um número par.');

// Regra assíncrona (Promise)
Vigia.rules.add('cep_existe', function (valor) {
    return fetch('https://viacep.com.br/ws/' + valor.replace(/\D/g, '') + '/json/')
        .then(r => r.json())
        .then(d => !d.erro || 'CEP não encontrado.');
});

// Uso: data-rules="required|cep|cep_existe"

Erros comuns

SintomaCausa e solução
Vigia.js precisa do axiosO axios não foi carregado antes do Vigia (ou não carregou). Inclua o script do axios antes.
"O servidor enviou uma resposta inesperada."O controller respondeu HTML ou texto (ex.: jexit(), aviso do PHP antes do JSON). Responda sempre com o ApiResponseHelper e confira se a URL leva format=json quando o componente exige.
403 em todo envioToken: falta JHtml::_('form.token') no formulário (Joomla 3) ou a sessão expirou. Com json: true, o JSession::checkToken() do Joomla 3 não lê o corpo JSON: use o envio padrão (multipart).
O erro do servidor não aparece no campoA chave em errors não corresponde ao name do campo. Confira a tabela de correspondência ou use data-error-for.
A regra funciona no navegador e não no servidorÉ uma regra só do navegador (remote, confirmed, password, placa…). Valide também no PHP.
Rótulo diferente entre navegador e servidorO navegador usa o <label>; o servidor, os rótulos do ValidationHelper. Passe os rótulos pelo clientConfig() para ficarem iguais.
Envio duplicadoNão junte @submit.prevent do Alpine ou outro onsubmit com o Vigia: ele já trata o envio e ignora cliques durante o carregamento.

Compatibilidade

  • Joomla 3.4.5+, 4 e 5. Token pelo campo do form.token (3) e pelo cabeçalho X-CSRF-Token e Joomla.getOptions('csrf.token') (4/5); mensagens pelo Joomla.renderMessages quando não há área no formulário.
  • Navegadores com suporte ao axios 1.x (Chrome, Edge, Firefox e Safari atuais). Sem Internet Explorer.
  • axios 1.x (obrigatório para enviar); Alpine.js 3.x (opcional).
  • Testado: as mesmas 84 combinações de dados e regras dão os mesmos erros e mensagens no Vigia e no ValidationHelper.
