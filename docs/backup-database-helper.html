BackupDatabaseHelper

Backup do banco MySQL/MariaDB ou PostgreSQL 10+ em um arquivo .sql (ou .sql.gz), em PHP puro, sem mysqldump nem pg_dump no servidor. Dois modos: só a estrutura (tabelas vazias, views e triggers) ou estrutura + dados. Salva numa pasta protegida do servidor ou envia direto para o navegador. Nunca apaga nada: nem no banco ao gerar, nem no banco de destino ao restaurar.

Visão geral

require_once JPATH_COMPONENT . '/helpers/BackupDatabaseHelper.php';   // puxa PlatformHelper e DbConnectionHelper

$r = BackupDatabaseHelper::full();                       // estrutura + dados do banco do Joomla
$r = BackupDatabaseHelper::schema();                     // só a estrutura
$r = BackupDatabaseHelper::full(['connection' => 'erp', 'gzip' => true]);   // outro banco, compactado

if ($r['success']) {
    echo $r['data']['caminho'];   // /var/www/site/backups/database/meusite_completo_20261112_101500_a1b2c3.sql
}
  • Depende de PlatformHelper (pasta raiz, log, nome seguro) e DbConnectionHelper (qual banco). Os dois são carregados sozinhos se estiverem na mesma pasta.
  • PHP 8.2+; Joomla 4.4, 5 e 6. Fora do Joomla (PHP puro, script CLI) funciona registrando a conexão no DbConnectionHelper, que usa o pacote joomla/database (Composer).
  • Bancos: MySQL 5.7+/8.x e MariaDB (driver mysqli ou pdomysql), PostgreSQL 10 ou mais novo (driver pgsql). Outro banco devolve erro sem gerar arquivo.
  • Não guarda o banco na memória: lê as tabelas em blocos e grava o arquivo (ou a resposta) enquanto lê. Serve para bancos grandes; o limite de tempo do PHP é desligado durante o backup.
  • Nunca lança exceção em schema(), full() e download*(): o erro volta em $r['success'] === false com a mensagem, e é registrado no log.

Dados sensíveis Um backup completo tem senhas (hash), e-mails, sessões e tokens. Antes de chamar, confira a permissão (PermissionHelper) e o token CSRF; prefira guardar os arquivos fora da pasta pública com setBaseDirectory().

Salvar no servidor: schema, full, save

MétodoRetornoO que faz
schema(array $opcoes = [])resultadoSó a estrutura: tabelas vazias (no MySQL, sem o AUTO_INCREMENT acumulado: o contador recomeça do 1), views e triggers.
full(array $opcoes = [])resultadoEstrutura + todos os dados (e, no PostgreSQL, o valor atual das sequências).
save($modo, array $opcoes = [])resultadoO mesmo, com o modo em variável: BackupDatabaseHelper::SCHEMA ('schema', 'estrutura', 'structure') ou ::FULL ('full', 'completo', 'data'). Outro valor devolve erro.

O arquivo é gravado primeiro como nome.sql.parcial e só ganha o nome final quando termina. Se o banco ou o disco falharem no meio, o .parcial fica na pasta com o aviso BACKUP INCOMPLETO no fim, para análise, e o caminho volta em $r['data']['arquivo_parcial'].

$r = BackupDatabaseHelper::full([
    'gzip'         => true,
    'exclude_data' => ['#__session'],      // sessões: só a estrutura
    'directory'    => 'diario',             // backups/database/diario/
]);

if (!$r['success']) {
    LogHelper::error('Backup diário falhou: ' . $r['mensagem']);
    return;
}

// $r['data']
// [
//   'modo' => 'full', 'banco' => 'meusite',
//   'tabelas' => 87, 'views' => 2, 'triggers' => 1, 'linhas' => 154320,
//   'snapshot' => true, 'segundos' => 4.81,
//   'arquivo' => 'meusite_completo_20261112_031500_9f2c1a.sql.gz',
//   'caminho' => '/var/www/site/backups/database/diario/meusite_completo_20261112_031500_9f2c1a.sql.gz',
//   'bytes'   => 18234411,
// ]

Baixar pelo navegador: downloadSchema, downloadFull, download

Gera o backup enquanto envia: nada fica guardado na memória, e o navegador começa a receber logo. Com 'save_copy' => true, grava ao mesmo tempo uma cópia no servidor (o caminho volta em $r['data']['copia']).

controllers/backup.php (administrador)
public function baixar()
{
    if (!PermissionHelper::requireToken('Sua sessão expirou. Recarregue a página.', 'get') || !PermissionHelper::require('core.admin', 'com_loja')) {
        return;
    }

    $modo = InputHelper::string('modo', 'full', 'get') === 'schema'
        ? BackupDatabaseHelper::SCHEMA
        : BackupDatabaseHelper::FULL;

    $r = BackupDatabaseHelper::download($modo, ['gzip' => true, 'save_copy' => true]);

    if (!$r['success'] && !headers_sent()) {
        // erro antes de começar o envio: tabela inexistente, banco não suportado, pasta sem permissão
        return ApiResponseHelper::error($r['mensagem']);
    }

    PlatformHelper::close();   // encerra aqui: o Joomla não manda o template junto com o arquivo
}
  • Erros de validação (tabela ou schema inexistente, banco não suportado, subpasta inválida) voltam no resultado antes de qualquer cabeçalho, então dá para responder com uma mensagem normal.
  • Se o banco falhar no meio do envio, o arquivo baixado termina com -- ATENÇÃO: BACKUP INCOMPLETO. Não use esse arquivo para restaurar.
  • Os buffers de saída abertos (template, ob_start()) são descartados antes do envio, para o arquivo não sair com HTML no começo.
  • Cabeçalhos: application/sql ou application/gzip, Content-Disposition: attachment, no-store (navegador e proxy não guardam cópia).

Opções

Todas opcionais, aceitas por todos os métodos de backup.

OpçãoPadrãoO que faz
connectionbanco do JoomlaNome registrado no DbConnectionHelper ou um driver pronto.
tablestodasSó estas tabelas/views (texto ou lista; aceita #__). Nome que não existe devolve erro. No PostgreSQL aceita 'schema.tabela'; tabela particionada leva junto as partições.
schemastodos, menos os do sistema(PostgreSQL) Só estes schemas. Schema que não existe devolve erro.
excludenenhumaTabelas/views que ficam de fora (aceita #__).
exclude_datanenhumaTabelas que entram só com a estrutura, sem as linhas: sessões, cache, logs volumosos.
prefix_onlyfalsetrue: só tabelas com o prefixo da conexão (ex.: jos_). Útil quando o banco é dividido com outro sistema.
viewstruefalse deixa as views de fora.
triggerstruefalse deixa os triggers de fora.
gzipfalseCompacta em .sql.gz (precisa da extensão zlib). Costuma reduzir o arquivo para 10–20%.
consistenttrueLê tudo num retrato único do banco, sem travar tabelas: um pedido gravado durante o backup não aparece pela metade. Veja Consistência.
directorypasta baseSubpasta dentro do diretório base ('diario', 'antes-da-migracao/v2'). .. devolve erro.
file_nameautomáticoNome do arquivo; a extensão é ajustada ao gzip e caminhos são descartados. Padrão: {banco}_{completo|estrutura}_{AAAAMMDD_HHMMSS}_{aleatório}.sql.
save_copyfalseSó no download: também grava uma cópia no servidor.
// Só as tabelas do componente, sem a de logs, compactado
$r = BackupDatabaseHelper::full([
    'tables'  => ['#__loja_pedidos', '#__loja_itens', '#__loja_clientes', '#__loja_log'],
    'exclude' => '#__loja_log',
    'gzip'    => true,
]);

// PostgreSQL: dois schemas e uma tabela de outro
$r = BackupDatabaseHelper::schema([
    'connection' => 'erp',
    'schemas'    => ['public', 'vendas'],
]);

Configuração

MétodoO que faz
setBaseDirectory($pasta)Pasta onde os backups ficam. Caminho absoluto ou relativo à raiz do site; é criada se não existir. Padrão: {raiz do site}/backups/database.
getBaseDirectory()Caminho absoluto em uso (cria a pasta padrão se preciso).
setChunkSize($linhas)Quantas linhas são lidas do banco por vez (padrão 1000). Diminua para tabelas com BLOBs grandes.
setRowsPerInsert($linhas)Quantas linhas vão em cada INSERT do arquivo (padrão 100). Cada INSERT também é limitado a ~1 MB, para caber no max_allowed_packet na restauração.
setLogCategory($categoria)Categoria dos registros de log (padrão backup_database_helper).
// Fora da pasta pública: o servidor web não consegue entregar o arquivo nem por engano
BackupDatabaseHelper::setBaseDirectory('/home/meusite/backups-banco');

Toda pasta usada recebe .htaccess (Apache), web.config (IIS) e index.html bloqueando o acesso pela web. Os arquivos são criados com permissão 0640 e as pastas com 0750. No Nginx, que ignora o .htaccess, a pasta padrão fica acessível se estiver dentro do site: use setBaseDirectory() fora dele ou bloqueie com location ^~ /backups/ { deny all; }.

Listar tabelas: tables

tables(array $opcoes = []) devolve as tabelas e views do banco, para montar a tela de escolha do que entra no backup. Aceita connection e, no PostgreSQL, schemas.

foreach (BackupDatabaseHelper::tables() as $t) {
    echo $t['nome'], ' (', $t['tipo'], ') ', FormatHelper::bytes($t['tamanho_bytes']), ' · ~', $t['linhas_aprox'], ' linhas';
}
// [
//   ['nome' => 'jos_content', 'tipo' => 'tabela', 'engine' => 'InnoDB', 'linhas_aprox' => 1520, 'tamanho_bytes' => 4210688],
//   ['nome' => 'jos_v_vendas', 'tipo' => 'view', 'engine' => null, 'linhas_aprox' => null, 'tamanho_bytes' => 0],
// ]

linhas_aprox é a estimativa do banco (no InnoDB pode errar bastante; o número exato vem em $r['data']['linhas'] depois do backup). No PostgreSQL, tabelas fora do schema public aparecem como schema.tabela, e engine é sempre null. Diferente dos métodos de backup, tables() lança exceção se a conexão falhar.

Nunca apaga nada

A regra do helper é que um backup não pode piorar a situação de ninguém, nem a do banco de origem, nem a do banco onde ele for restaurado.

OndeGarantia
Banco de origem (MySQL)Só executa SELECT e SHOW, mais o fuso/charset da sessão (restaurados no final) e a transação de leitura (terminada em ROLLBACK). Qualquer outro comando é recusado antes de chegar ao banco.
Banco de origem (PostgreSQL)Além disso, tudo roda numa transação READ ONLY: o próprio servidor recusa qualquer escrita. As configurações usam SET LOCAL e somem no ROLLBACK final.
Arquivo geradoSem DROP, DELETE, TRUNCATE, REPLACE nem UPDATE. Cada comando passa por uma lista do que é permitido antes de ir para o arquivo.
Restauração (MySQL)CREATE TABLE IF NOT EXISTS e INSERT IGNORE: tabela que já existe fica como está, registro com a mesma chave não é sobrescrito.
Restauração (PostgreSQL)IF NOT EXISTS; tipos, funções, views, triggers e chaves estrangeiras em blocos DO que ignoram o objeto se ele já existir; dados com ON CONFLICT DO NOTHING; nada usa OR REPLACE; o único ALTER é ADD CONSTRAINT; sequências só avançam (setval nunca volta o contador).
Arquivos de backupNunca sobrescreve nem remove: cada backup ganha um nome único, e o arquivo é aberto em modo exclusivo. Não existe método de limpeza de backups antigos, de propósito.

Tabela sem chave INSERT IGNORE/ON CONFLICT só reconhecem "mesmo registro" pela chave primária ou única. Tabela sem nenhuma das duas recebe as linhas de novo se o arquivo for restaurado duas vezes no mesmo banco.

Restaurar não é sincronizar Como nada é sobrescrito, restaurar sobre um banco que já tem os registros não volta os valores antigos: o registro alterado depois do backup continua alterado. Para voltar um banco ao estado do backup, restaure num banco vazio (ou novo) e troque.

O que vai no arquivo

BancoOrdem
MySQL / MariaDBCabeçalho (charset utf8mb4, fuso UTC, checagem de chave estrangeira desligada durante a carga) → para cada tabela, CREATE TABLE e os dados → triggers → views (na ordem de dependência) → rodapé que restaura as variáveis da sessão.
PostgreSQLSchemas → extensões → tipos (enum, domínio, composto) → funções e procedures → sequências → tabelas (identity, colunas geradas, partições, herança, UNLOGGED) → dados → valor das sequências → índices → chaves estrangeiras → triggers → views e views materializadas (na ordem de dependência).
  • Triggers depois dos dados: não disparam durante a restauração (um trigger que grava log não duplica o log).
  • Datas: lidas e gravadas em UTC; TIMESTAMP/timestamptz voltam iguais em servidor com outro fuso.
  • Texto: utf8mb4/UTF8; emojis e acentos não viram ?.
  • Binários (BLOB, VARBINARY, geometria) saem em hexadecimal, BIT como número e bytea em hex: o arquivo é texto puro, seguro para abrir e transferir.
  • Colunas geradas (VIRTUAL/STORED) entram na estrutura, mas não nos INSERTs: o banco recalcula.
  • MySQL: o DEFINER de views e triggers é removido (o usuário que restaura vira o dono; o do servidor original pode não existir no destino).
  • PostgreSQL: chave estrangeira para uma tabela que ficou fora do backup vira só um comentário no arquivo. Permissões (GRANT), donos, políticas de linha (RLS), estatísticas e objetos de extensões não entram.
  • Não entram procedures/functions/eventos do MySQL, nem usuários do banco.

Consistência (consistent)

Com 'consistent' => true (padrão), o MySQL abre START TRANSACTION WITH CONSISTENT SNAPSHOT, READ ONLY e o PostgreSQL REPEATABLE READ, READ ONLY: todas as tabelas são lidas como estavam no mesmo instante, sem travar ninguém. Vale para tabelas transacionais (InnoDB); tabelas MyISAM continuam sendo lidas como estão no momento da leitura.

SituaçãoO que acontece
MySQL, conexão já dentro de uma transação (DbTransactionHelper::run)O backup roda sem snapshot (abrir outra transação confirmaria a sua) e devolve 'snapshot' => false.
PostgreSQL, conexão já dentro de uma transaçãoDevolve erro "Há uma transação aberta nesta conexão": não dá para garantir o modo somente leitura, e encerrar a transação de outra rotina não é papel do backup.
MySQL antigo sem READ ONLYSegue sem snapshot.

Chame o backup fora de transações. Em rotinas que gravam e depois fazem backup, registre uma segunda conexão para o mesmo banco no DbConnectionHelper e passe-a em connection.

Restaurar

-- MySQL / MariaDB
mysql -u usuario -p banco_destino < meusite_completo_20261112_031500_9f2c1a.sql
gunzip -c meusite_completo_20261112_031500_9f2c1a.sql.gz | mysql -u usuario -p banco_destino

-- PostgreSQL
psql -d banco_destino -f erp_completo_20261112_031500_4b7e10.sql
gunzip -c erp_completo_20261112_031500_4b7e10.sql.gz | psql -d banco_destino
  • O arquivo usa DELIMITER nos triggers do MySQL: restaure pelo cliente mysql (ou phpMyAdmin/Adminer/HeidiSQL, que entendem DELIMITER), não com um $db->execute() do arquivo inteiro.
  • MySQL, segunda restauração no mesmo banco: o MySQL não tem CREATE VIEW IF NOT EXISTS (o MariaDB tem), então a primeira view já existente dá erro "Table '...' already exists". Como as views ficam no fim do arquivo, as tabelas, os dados e os triggers já foram restaurados nesse ponto; use mysql --force para seguir até o fim.
  • Restaurar no banco de origem também é seguro: nada é apagado ou sobrescrito, apenas o que falta é criado.

Receitas

Backup diário pelo cron

Um script CLI chamado pelo cron, com LockHelper para não rodar dois ao mesmo tempo:

cli/backup-diario.php
// carregue o Joomla em modo CLI como os outros scripts do componente (veja fila/cli/queue-worker.php)
require_once JPATH_ADMINISTRATOR . '/components/com_loja/helpers/BackupDatabaseHelper.php';
require_once JPATH_ADMINISTRATOR . '/components/com_loja/helpers/LockHelper.php';

BackupDatabaseHelper::setBaseDirectory('/home/meusite/backups-banco');

$execucao = LockHelper::run('backup-diario', function () {
    return BackupDatabaseHelper::full([
        'gzip'         => true,
        'directory'    => 'diario',
        'exclude_data' => ['#__session', '#__action_logs'],
    ]);
});

if (!$execucao['acquired']) {
    fwrite(STDERR, "Outro backup ainda está rodando.\n");
    exit(1);
}

$r = $execucao['result'];
echo $r['mensagem'], PHP_EOL;
exit($r['success'] ? 0 : 1);
# crontab: todo dia às 3h15
15 3 * * * php /var/www/site/administrator/components/com_loja/cli/backup-diario.php >> /var/log/backup-loja.log 2>&1

Os backups antigos não são apagados pelo helper. Para manter só os últimos dias, use a rotação do próprio servidor (por exemplo, find /home/meusite/backups-banco/diario -name '*.sql.gz' -mtime +14 -delete no cron), onde fica claro o que está sendo removido.

Antes de uma atualização do componente

// script de instalação/atualização: só a estrutura e os dados das tabelas do componente
$r = BackupDatabaseHelper::full([
    'tables'    => ['#__loja_pedidos', '#__loja_itens', '#__loja_clientes'],
    'directory' => 'antes-da-atualizacao',
    'file_name' => 'loja_antes_v' . $versaoNova,
    'gzip'      => true,
]);

if (!$r['success']) {
    throw new RuntimeException('Atualização cancelada: o backup falhou (' . $r['mensagem'] . ').');
}

MensagemCausa

Falha ao gravar o backup (disco cheio ou conexão encerrada?).Disco cheio, ou o navegador cancelou o download.
  • É um backup lógico (comandos SQL). Para bancos de dezenas de GB, ou quando precisa de recuperação até o minuto, use as ferramentas do servidor (mysqldump --single-transaction, pg_dump, backups físicos do provedor).
  • Pela web, o tempo máximo é o do servidor web/proxy (o do PHP é desligado). Backups grandes: cron/CLI ou fila.
  • O helper não envia o arquivo para outro lugar (S3, FTP, e-mail). Um backup que fica só no mesmo servidor do banco não protege contra a perda do servidor.
