Guia: fila de jobs

Tarefas demoradas em segundo plano, do zero à produção: criar o job, enfileirar, rodar o worker, mostrar o progresso e lidar com erros.

Visão geral

Algumas tarefas demoram demais para acontecer enquanto o usuário espera a página carregar: importar um CSV com 200 mil linhas, gerar 3 mil PDFs, enviar e-mails em massa, chamar uma API lenta. A fila de jobs resolve isso. O controller só anota o trabalho numa tabela e responde na hora. Um processo separado, o worker, executa o trabalho em segundo plano, com progresso, novas tentativas em caso de erro e recuperação se o servidor cair.

Ciclo de vida de um job

pending ──next()──> processing ──complete()──> completed
   ^                    │
   │                    ├──release()──> pending   (pausa: volta à fila sem gastar tentativa)
   │                    ├──fail()─────> retry     (volta depois de uma espera)
   │                    │          └──> failed    (sem tentativas restantes)
   │                    └──worker morreu (lock expirado)──> retry ou failed
   └──retry()── failed / cancelled             cancel() ──> cancelled
StatusSignificaSai dele com
pendingEsperando um worker.next(), cancel()
processingUm worker está executando. Tem lock_token.complete(), release(), fail(), cancel(…, true), lock expirado
retryDeu erro e vai tentar de novo depois de disponivel_em.next(), cancel()
completedConcluído com sucesso. Final.—
failedEsgotou as tentativas, ou falhou de vez. Final.retry() manual
cancelledCancelado. Final.retry() manual

Passo a passo

1. Copie os arquivos

Mantenha a pasta fila/ ao lado do QueueHelper.php: o worker CLI encontra os arquivos por essa posição.

│       ├── AbstractJob.php
│       ├── JobRegistry.php

└── jobs/

    └── GerarRelatorioJob.php     ← seus jobs (passo 3)

2. Crie a tabela

Escolha uma forma:

FormaComo
No SQL de instalação do componenteCopie fila/table.sql (MySQL) ou fila/table.postgresql.sql para o seu install.mysql.utf8.sql / install.postgresql.utf8.sql.

3. Escreva o job

Um job é uma classe que herda AbstractJob e implementa handle(). Os dados chegam pelo getPayload().

components/com_seucomp/jobs/GerarRelatorioJob.php
<?php

defined('_JEXEC') or die;

class GerarRelatorioJob extends AbstractJob
{
    public function handle()
    {
        $mes = (int) $this->getPayload('mes');
        $ano = (int) $this->getPayload('ano');

        if ($mes < 1 || $mes > 12) {
            // Dado inválido não melhora tentando de novo: falha de vez.
            return $this->fail('Mês inválido: ' . $mes, true);
        }

        $arquivo = RelatorioService::gerar($mes, $ano);   // seu código

        // O array devolvido vira o resultado do job (veja status()).
        return [
            'arquivo' => $arquivo,
            'gerado_em' => date('c'),
        ];
    }
}
Se o handle()…O worker faz
devolve um array (ou nada)Conclui o job com esse array como resultado.
chama $this->complete([...])Nada: o job já foi concluído.
chama $this->release()Nada: o job volta à fila para continuar depois (jobs longos).
chama $this->fail('motivo')Nada: o erro foi registrado e o job vai para retry ou failed.
lança uma exceçãoRegistra a falha com a mensagem e o arquivo/linha.
causa erro fatal, estoura o tempo ou chama exitRegistra a falha antes de o processo morrer e desfaz a transação aberta.

4. Registre o job

Crie um arquivo que registra todos os jobs. Ele é carregado em dois lugares: no componente (para o push() saber a fila de cada tipo) e no worker (opção --bootstrap).

components/com_seucomp/jobs/jobs.php
<?php

defined('_JEXEC') or die;

$base = JPATH_SITE . '/components/com_seucomp';

// No worker estas classes já vêm carregadas.
if (!class_exists('QueueHelper')) {
    require_once $base . '/helpers/QueueHelper.php';
    require_once $base . '/helpers/fila/AbstractJob.php';
    require_once $base . '/helpers/fila/JobRegistry.php';
}

//                    tipo                arquivo da classe                     classe               fila
JobRegistry::register('gerar_relatorio', $base . '/jobs/GerarRelatorioJob.php', 'GerarRelatorioJob', 'relatorios');
JobRegistry::register('enviar_email',    $base . '/jobs/EnviarEmailJob.php',    'EnviarEmailJob',    'emails');

// Opcional: grava os logs da fila em components/com_seucomp/logs/queue_helper.php
QueueHelper::setLogDirectory('components/com_seucomp/logs');

5. Enfileire no controller

controllers/relatorios.php
require_once JPATH_COMPONENT . '/jobs/jobs.php';

class SeucompControllerRelatorios extends JControllerLegacy
{
    public function gerar()
    {
        JSession::checkToken() or jexit('Token inválido');

        $r = QueueHelper::push('gerar_relatorio', [
            'mes' => InputHelper::uint('mes', 0, 'post'),
            'ano' => InputHelper::uint('ano', 0, 'post'),
        ], [
            'usuario_id' => (int) JFactory::getUser()->id,
            'unico' => true,          // dois cliques não geram dois relatórios iguais
        ]);

        if (!$r['success']) {
            return ApiResponseHelper::error($r['mensagem']);
        }

        return ApiResponseHelper::created('Relatório na fila.', ['uuid' => $r['data']['uuid']]);
    }
}

O uuid é o identificador para mostrar ao usuário e consultar o andamento. Prefira-o ao id: ele não é sequencial, então ninguém adivinha o job de outra pessoa.

7. Mostre o andamento na tela

controllers/relatorios.php
public function status()
{
    $r = QueueHelper::status(
        InputHelper::string('uuid', '', 'get'),
        (int) JFactory::getUser()->id        // só o dono consulta
    );

    if (!$r['success']) {
        return ApiResponseHelper::notFound($r['mensagem']);
    }

    $job = $r['data'];

    return ApiResponseHelper::success('Status.', [
        'status' => $job['status'],
        'percentual' => $job['percentual'],
        'finalizado' => $job['finalizado'],
        'resultado' => $job['status'] === 'completed' ? $job['resultado'] : null,
        'erro' => $job['status'] === 'failed' ? 'Não foi possível gerar o relatório.' : null,
    ]);
}
media/com_seucomp/js/relatorio.js
function acompanhar(uuid) {
    fetch('index.php?option=com_seucomp&task=relatorios.status&format=json&uuid=' + uuid)
        .then(function (r) { return r.json(); })
        .then(function (resposta) {
            var job = resposta.data;
            document.querySelector('#barra').style.width = job.percentual + '%';

            if (!job.finalizado) {
                setTimeout(function () { acompanhar(uuid); }, 2000);
            } else if (job.status === 'completed') {
                window.location = job.resultado.arquivo;
            } else {
                alert(job.erro || 'O processamento foi interrompido.');
            }
        });
}

O texto de erro do job pode conter detalhes técnicos (arquivo, linha, SQL). Mostre ao usuário uma mensagem própria e deixe o erro completo para o administrador.

Mantendo o worker rodando

AmbienteComoComando
Servidor com cron (o mais comum)O cron inicia um worker por minuto, que trabalha até 55s ou até a fila esvaziar.--max-time=55 --stop-when-empty
VPS / servidor próprioUm worker permanente por fila, reiniciado pelo supervisor ou systemd se cair.--queue=emails --max-time=0
Hospedagem sem linha de comandoUma URL protegida, chamada por um cron externo.veja abaixo

Cron

# crontab -e   (usuário do site, nunca root)
* * * * * php /var/www/site/components/com_seucomp/helpers/fila/cli/queue-worker.php --bootstrap=/var/www/site/components/com_seucomp/jobs/jobs.php --max-time=55 --stop-when-empty --quiet

# limpeza diária dos jobs finalizados há mais de 30 dias (veja purge())
30 3 * * * php /var/www/site/components/com_seucomp/cli/limpar-fila.php

Sem --max-time, o worker sai depois de 240 segundos. Esse padrão evita que um cron sem opções acumule processos. Workers sobrepostos não causam problema: dois workers nunca pegam o mesmo job.

Supervisor ou systemd

/etc/supervisor/conf.d/fila-emails.conf
[program:fila-emails]
command=php /var/www/site/components/com_seucomp/helpers/fila/cli/queue-worker.php --bootstrap=/var/www/site/components/com_seucomp/jobs/jobs.php --queue=emails --max-time=3600
user=www-data
numprocs=2
process_name=%(program_name)s_%(process_num)02d
autorestart=true
stopsignal=TERM
stopwaitsecs=300
stdout_logfile=/var/log/fila-emails.log
redirect_stderr=true

--max-time=3600 faz o worker sair a cada hora e o supervisor iniciar outro: assim, alterações no código dos jobs entram em vigor e eventuais vazamentos de memória são zerados. Depois de publicar código novo, reinicie os workers (supervisorctl restart fila-emails:*): um worker em execução continua com o código antigo carregado.

Ao receber SIGTERM (deploy, reinício), o worker termina o job atual e sai. Por isso stopwaitsecs deve ser maior que o timeout_seconds dos jobs. Um segundo sinal encerra na hora.

Hospedagem sem linha de comando

O QueueWorker roda em qualquer contexto, inclusive num controller. Crie uma tarefa protegida por um segredo e chame-a a cada minuto por um serviço de cron externo (cron-job.org, EasyCron, o cron do painel da hospedagem):

controllers/fila.php
public function processarFila()
{
    $segredo = JComponentHelper::getParams('com_seucomp')->get('segredo_fila');

    if ($segredo === '' || !hash_equals($segredo, InputHelper::string('chave', '', 'get'))) {
        return ApiResponseHelper::forbidden();
    }

    require_once JPATH_COMPONENT . '/jobs/jobs.php';
    require_once JPATH_COMPONENT . '/helpers/fila/QueueWorker.php';

    ignore_user_abort(true);

    $resumo = QueueWorker::run([
        'max_time' => 25,             // abaixo do max_execution_time do servidor
        'stop_when_empty' => true,
        'sleep' => 1,
    ]);

    return ApiResponseHelper::success('Fila processada.', $resumo);
}
curl -s "https://seusite.com.br/index.php?option=com_seucomp&task=fila.processarFila&format=json&chave=SEGREDO"

Pela web, o tempo de cada execução é limitado pelo servidor (normalmente 30 a 120 segundos). Use jobs em fatias e timeout_seconds menores que esse limite.

Jobs longos: processamento em fatias

Um job que leva mais tempo que o permitido deve trabalhar em fatias: processa um pedaço, salva onde parou com progress() e chama release(). O job volta à fila e, na próxima execução, continua do ponto salvo. release() não gasta tentativa: um arquivo pode precisar de 500 fatias sem nunca falhar por isso.

class ImportarClientesJob extends AbstractJob
{
    public function handle()
    {
        $arquivo = new SplFileObject($this->getPayload('caminho'));
        $arquivo->seek(PHP_INT_MAX);
        $total = $arquivo->key();                 // número de linhas

        $linha = (int) $this->getProgress();      // onde a execução anterior parou (0 na primeira)
        $arquivo->seek($linha);

        while (!$arquivo->eof()) {
            $dados = $arquivo->fgetcsv();
            $linha++;

            if ($dados !== false && $dados !== [null]) {   // [null] = linha em branco
                $this->importarLinha($dados);
            }


            if ($linha % 500 === 0) {
                $this->progress($linha, $total);  // salva o ponto e renova o lock

                if ($this->shouldStop()) {        // tempo acabando, cancelado ou worker encerrando
                    return $this->release();      // continua na próxima execução
                }
            }
        }

        return $this->complete(['linhas' => $linha]);
    }
}
shouldStop() devolve true quando…Porque
faltam menos de 10 segundos para o timeout_seconds do jobSair antes de o worker interromper a execução.
o job foi cancelado pelo usuário (cancel(…, true))Não adianta continuar: ele não pode mais ser concluído.
o lock foi perdido (outro worker assumiu o job)Evita dois workers processando o mesmo job.
o worker recebeu SIGTERM/SIGINTDeploy ou reinício: sai limpo em vez de ser morto no meio.

Se o job foi cancelado, release() devolve false e nada acontece: o job continua cancelado. Não é preciso tratar esse caso à parte.

Erros e novas tentativas

Cada execução que termina em erro gasta uma tentativa (max_tentativas, padrão 3). Entre as tentativas, a espera dobra: 30s, 60s, 120s… até 1 hora. Esgotadas as tentativas, o job vai para failed.

SituaçãoUseResultado
Erro passageiro (API fora do ar, timeout de rede, deadlock)Lance a exceção, ou $this->fail('motivo')Tenta de novo depois da espera.
Erro permanente (dado inválido, registro apagado)$this->fail('motivo', true)failed na hora, sem gastar as outras tentativas.
Serviço externo pediu para esperar (HTTP 429)$this->release(120, true)Volta em 2 minutos, contando como tentativa.
Pausa de um job em fatias$this->release()Volta na hora, sem gastar tentativa.
Worker morreu (servidor reiniciou, processo morto)Nada: é automáticoDepois de retry_after_seconds sem sinal, volta para retry.

Escreva jobs que podem rodar mais de uma vez. Se o worker morrer depois de enviar o e-mail e antes de marcar o job como concluído, o job vai rodar de novo. Guarde o que já foi feito (uma coluna enviado_em, o ponto salvo em progress()) e confira antes de repetir.

Avisando na última tentativa

public function handle()
{
    try {
        $this->chamarApi();
    } catch (Exception $e) {
        if ($this->isLastAttempt()) {
            Notificacao::admin('Job ' . $this->getUuid() . ' falhou de vez: ' . $e->getMessage());
        }

        throw $e;     // o worker registra a falha
    }
}

Tempo de execução e locks

Dois tempos controlam um job. Ambos podem ser definidos por job no push(), ou como padrão com os setDefault…().

OpçãoPadrãoO que faz
timeout_seconds240Tempo máximo de uma execução. O worker limita o PHP a esse tempo + 15s; shouldStop() e remainingSeconds() usam esse valor.
retry_after_seconds300Tempo sem sinal de vida para considerar o worker morto. Cada progress() ou heartbeat() renova o prazo.

Regra prática: mantenha retry_after_seconds maior que timeout_seconds, ou chame progress()/heartbeat() com frequência. Se um job ficar mais de retry_after_seconds sem sinal, outro worker o assume e ele passa a rodar duas vezes ao mesmo tempo. O primeiro worker percebe na próxima chamada a progress() ou shouldStop(), mas o trabalho já feito em paralelo não é desfeito.

No Linux, o limite de tempo do PHP conta só o tempo de CPU. Esperas por banco, rede ou sleep() não contam. Um job que passa a maior parte do tempo esperando uma API não é interrompido pelo limite: é por isso que shouldStop() usa o relógio de verdade. Em laços longos, use shouldStop().

Cancelamento

// Job ainda na fila: cancela na hora.
QueueHelper::cancel($uuid, $userId);

// Job em processamento: só com força. O worker não é interrompido, mas
// progress()/heartbeat()/shouldStop() passam a indicar a perda do job e
// complete() não tem mais efeito.
QueueHelper::cancel($uuid, $userId, true);

// Recolocar na fila um job cancelado ou falho
QueueHelper::retry($uuid, $userId);

O QueueHelper detecta sozinho as classes disponíveis. O mesmo queue-worker.php serve para as três versões: ele identifica a versão pela pasta libraries e inicia o Joomla do jeito certo. Tudo foi testado em Joomla 3.10, 4.4 e 5.2, inclusive erro fatal, estouro de tempo, exit(), SIGTERM e 8 workers em paralelo sobre 300 jobs.

Todas as datas da tabela ficam em UTC, como no restante do Joomla. Para exibir, converta com JHtml::_('date', $job['criado_em'], 'd/m/Y H:i'). Ao agendar com disponivel_em, informe em UTC, ou use delay_seconds.
