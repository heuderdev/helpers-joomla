DbTransactionHelper

Transações "tudo ou nada" com savepoints, retry automático em deadlock e uma transação independente por conexão.

Visão geral

Uma transação garante que um conjunto de gravações aconteça por inteiro ou não aconteça. O DbTransactionHelper cuida de tudo: abre a transação, confirma no final, desfaz se houver exceção, usa savepoints quando uma transação está dentro de outra e repete automaticamente em caso de deadlock.

$pedido = DbTransactionHelper::run(function () use ($clienteId, $itens) {
    $pedido = OrmTables::table('#__loja_pedidos')->create([
        'cliente_id' => $clienteId,
        'status' => 'aberto',
    ]);

    foreach ($itens as $item) {
        OrmTables::table('#__loja_pedido_itens')->create([
            'pedido_id' => $pedido->id,
            'produto_id' => $item['produto_id'],
            'quantidade' => $item['quantidade'],
        ]);
    }

    return $pedido;   // o retorno do callback é o retorno de run()
});
O callback…Resultado
termina normalmenteCOMMIT. run() devolve o que o callback devolveu.
lança qualquer exceçãoROLLBACK. run() relança a mesma exceção, com o tipo original.
sofre deadlock / lock timeoutROLLBACK, espera um pouco e executa o callback de novo (até retries vezes).

run(): o jeito recomendado

run()estático

DbTransactionHelper::run(callable $callback, array $options = []): mixed

Executa $callback dentro de uma transação. O callback recebe dois parâmetros, ambos opcionais: o driver da conexão e o número da tentativa (1, 2, 3…).

ParâmetroTipoDescrição
$callbackcallablefunction ($db, $tentativa) { … }
$optionsarrayVeja a tabela de opções abaixo.

Retorna: o valor devolvido pelo callback.

$resultado = DbTransactionHelper::run(
    function ($db, $tentativa) {
        // $db: driver do Joomla da conexão usada
        // $tentativa: 1 na primeira execução, 2 no primeiro retry…
        return OrmTables::table('#__loja_produtos')->increment(10, 'estoque', 5);
    },
    [
        'retries' => 3,
        'context' => ['produto_id' => 10, 'usuario' => JFactory::getUser()->id],
    ]
);
OpçãoTipoPadrãoDescrição
connectionstring|object|nullnullConexão onde a transação acontece: nome registrado no DbConnectionHelper, driver ou null para a do Joomla.
retriesint (0–10)3Quantas vezes repetir em deadlock/lock timeout. 0 desliga. Com 3, são até 4 execuções.
contextarray[]Dados extras gravados no log e na auditoria (ids, usuário…).
audit_eventstring''Nome do evento de auditoria. Só tem efeito com auditoria ligada.

Quando o callback é repetido

O callback só é executado de novo quando todas as condições abaixo valem:

  • o erro é de concorrência: deadlock ou lock timeout no MySQL (códigos 1205 e 1213), deadlock ou falha de serialização no PostgreSQL (SQLSTATE 40P01 e 40001);
  • esta é a transação mais externa da conexão. Transações aninhadas nunca repetem sozinhas: o erro sobe e a externa repete tudo, porque um deadlock desfaz a transação inteira;
  • ainda há tentativas: tentativa <= retries.

Entre as tentativas há uma espera que dobra a cada vez: 250 ms, 500 ms, 1 s… (máximo 5 s). Qualquer outro erro (duplicidade, SQL inválido, exceção sua) nunca é repetido.

Efeitos colaterais

Como o callback pode rodar mais de uma vez, ele deve conter apenas operações de banco. Envie e-mails, chame APIs ou grave arquivos depois do run():

$pedido = DbTransactionHelper::run(function () use ($dados) {
    return PedidoService::gravar($dados);    // só banco
});

EmailHelper::enviarConfirmacao($pedido);      // depois do COMMIT

Se o callback não puder ser repetido, passe ['retries' => 0].

Transações aninhadas (savepoints)

Chamar run() dentro de outro run() na mesma conexão cria um savepoint. Se o trecho interno falhar, só ele é desfeito, e a transação externa decide o que fazer.

DbTransactionHelper::run(function () use ($lote) {          // BEGIN
    foreach ($lote as $item) {
        try {
            DbTransactionHelper::run(function () use ($item) {  // SAVEPOINT
                ImportadorService::gravar($item);
            });                                                 // RELEASE SAVEPOINT
        } catch (RuntimeException $e) {
            // ROLLBACK TO SAVEPOINT: só este item foi desfeito
            LogHelper::write('warning', 'Item ignorado: ' . $e->getMessage());
        }
    }
});                                                             // COMMIT

Isso permite compor funções: um service que usa run() funciona tanto sozinho (com transação própria) quanto chamado de dentro de outra transação (como savepoint), sem mudar nada.

No PostgreSQL, depois de qualquer erro de SQL a transação fica bloqueada até um rollback. Capturar o erro só funciona se o trecho estiver num run() aninhado, como acima. Veja o guia de PostgreSQL.

Uma transação por conexão

Cada conexão tem a sua própria transação. Um run() no ERP dentro de um run() no banco do Joomla abre uma transação independente no ERP, não um savepoint. As duas são confirmadas separadamente, e não existe garantia de "tudo ou nada" entre bancos diferentes. Veja o padrão recomendado no guia de múltiplos bancos.

attempt() e transaction()

attempt()estático

DbTransactionHelper::attempt(callable $callback, array $options = []): array

Igual a run(), mas nunca lança exceção: devolve um array com o resultado. O erro técnico vai só para o log. Útil quando você quer responder sem try/catch.

Retorna: array com as chaves abaixo.

$resultado = DbTransactionHelper::attempt(function () use ($id) {
    return OrmTables::table('#__loja_produtos')->update($id, ['ativo' => 0]);
});

if (!$resultado['success']) {
    return ApiResponseHelper::error($resultado['mensagem']);
}

return ApiResponseHelper::success('Produto desativado.', $resultado['data']);
ChaveSucessoFalha
successtruefalse
status'sucesso''erro'
mensagem'Transação concluída com sucesso.''Não foi possível concluir a operação no banco de dados.'
dataretorno do callbacknull
errornullnull (o detalhe fica no log)

Com attempt() você perde o tipo da exceção. Para responder diferente a erros de regra de negócio (por exemplo, "estoque insuficiente") e erros técnicos, use run() com try/catch.

transaction()estático

DbTransactionHelper::transaction(callable $callback, array $options = []): mixed

Sinônimo de run(), com o mesmo comportamento.

Controle manual: begin, commit, rollback

Para os raros casos em que um callback não serve. Prefira run(): no controle manual, esquecer um rollback() deixa a transação aberta.

Estes três métodos não lançam exceção: devolvem false e registram o erro no log. Sempre confira o retorno.

if (!DbTransactionHelper::begin()) {
    throw new RuntimeException('Não foi possível iniciar a transação.');
}

try {
    OrmTables::table('#__loja_produtos')->update(10, ['preco' => 9.90]);
    OrmTables::table('#__loja_precos_historico')->create(['produto_id' => 10, 'preco' => 9.90]);

    if (!DbTransactionHelper::commit()) {
        throw new RuntimeException('Falha ao confirmar.');
    }
} catch (Throwable $e) {
    DbTransactionHelper::rollback();
    throw $e;
}
MétodoRetornoDescrição
begin($connection = null)boolAbre uma transação, ou um savepoint se já houver uma aberta.
commit($connection = null)boolConfirma o nível atual. false se não houver transação aberta.
rollback($connection = null)boolDesfaz o nível atual. Sem transação aberta, não faz nada e devolve true.

O controle manual não repete em deadlock: retry só existe em run()/attempt().

Consultando o estado

MétodoRetornoDescrição
isActive($connection = null)boolHá transação aberta nesta conexão?
depth($connection = null)int0 = nenhuma; 1 = transação; 2 ou mais = savepoints.
DbTransactionHelper::run(function () {
    DbTransactionHelper::isActive();       // true
    DbTransactionHelper::depth();          // 1
    DbTransactionHelper::isActive('erp');  // false: outra conexão
});

Configuração global

Valem para todas as chamadas seguintes no mesmo request. Configure no carregamento do componente.

setMaxRetries()estático

DbTransactionHelper::setMaxRetries(int $maxRetries): void

Padrão de retries quando a opção não é passada. Aceita de 0 a 10; padrão 3. Fora dessa faixa, lança InvalidArgumentException.

setRetryDelayMicroseconds()estático

DbTransactionHelper::setRetryDelayMicroseconds(int $microseconds): void

Espera antes do primeiro retry, em microssegundos (padrão 250000 = 250 ms). Dobra a cada tentativa, até 5 s.

setRetryableErrorCodes()estático

DbTransactionHelper::setRetryableErrorCodes(array $codes): void

Substitui a lista de códigos de erro que disparam retry. Padrão: ['1205', '1213', '40001', '40P01']. Mensagens conhecidas de deadlock continuam sendo reconhecidas mesmo fora da lista.

// Mantém os padrões e acrescenta 55P03 (lock_not_available, PostgreSQL)
DbTransactionHelper::setRetryableErrorCodes(['1205', '1213', '40001', '40P01', '55P03']);

setAuditEnabled()estático

DbTransactionHelper::setAuditEnabled(bool $enabled): void

Liga a auditoria (padrão: desligada). Com ela ligada e a opção audit_event em run(), cada transação gera um registro via AuditHelper::custom(): o evento com status => 'committed' no sucesso, ou evento.failed com o erro em cada tentativa que falhar. Sem a classe AuditHelper carregada, não faz nada.

DbTransactionHelper::setAuditEnabled(true);

DbTransactionHelper::run(function () use ($id) {
    OrmTables::table('#__loja_pedidos')->update($id, ['status' => 'cancelado']);
}, [
    'audit_event' => 'pedido.cancelado',
    'context' => ['pedido_id' => $id],
]);

setLogCategory() / setLogDirectory()estático

DbTransactionHelper::setLogCategory(string $category): void DbTransactionHelper::setLogDirectory(string $directory): void

Categoria (padrão 'db_transaction') e diretório dos logs. O helper usa LogHelper::write() se essa classe estiver carregada; senão, JLog::add(). O diretório só é usado pelo LogHelper.

O que vai para o log

NívelEvento
debugInício, commit e savepoints; transação concluída.
warningRollback; falha que vai ser repetida.
errorFalha que não será repetida; falha em begin/commit/rollback manuais.
criticalO próprio rollback falhou depois de um erro.

Cuidados

  • MySQL: comandos de estrutura (CREATE, ALTER, DROP, TRUNCATE) fazem commit implícito e encerram a transação aberta. Não os use dentro de run().
  • MySQL: tabelas MyISAM ignoram transações. Use InnoDB.
  • Transações curtas: linhas alteradas ficam travadas até o fim. Não faça chamadas lentas (HTTP, arquivos grandes) lá dentro.
  • Exceções: qualquer Throwable causa rollback, inclusive TypeError e exceções suas.
