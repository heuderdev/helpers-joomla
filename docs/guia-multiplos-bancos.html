Guia: múltiplos bancos

Consulte outros bancos ao lado do Joomla, e entenda o que dá e o que não dá para garantir quando se grava em dois bancos.

Quando usar

Quando o componente precisa ler ou gravar em outro banco além do Joomla: um ERP, um sistema legado, uma réplica só de leitura para relatórios. Os dois bancos podem ser de tipos diferentes (por exemplo, Joomla em MySQL e ERP em PostgreSQL), e tudo continua funcionando com a mesma API.

Configurar em três passos

  1. Registre a conexão com um nome, uma vez, no carregamento do componente:

    if (!DbConnectionHelper::has('erp')) {
    DbConnectionHelper::register('erp', [
        'driver' => 'pgsql',
        'host' => $params->get('erp_host'),
        'user' => $params->get('erp_user'),
        'password' => $params->get('erp_password'),
        'database' => 'erp',
        'prefix' => 'erp_',
    ]);
}

  2. Aponte as consultas para ela, de uma destas formas:

    // No model (todas as consultas do model vão para o ERP)
class ClienteErpModel extends OrmBase
{
    protected $table = '#__clientes';
    protected $connection = 'erp';
}

// Pontual, sem model
OrmTables::table('#__clientes', ['connection' => 'erp'])->get();

// Registrada por nome
OrmTables::register('clientesErp', '#__clientes', ['connection' => 'erp']);
OrmTables::get('clientesErp')->get();

  3. Use transações passando a conexão:

    DbTransactionHelper::run(function () {
    ClienteErpModel::query()->update(5, ['ativo' => false]);
}, ['connection' => 'erp']);

O prefixo #__ é trocado pelo prefix de cada conexão: #__clientes vira jos_clientes no Joomla e erp_clientes no ERP. Se as tabelas do outro banco não têm prefixo, use 'prefix' => '' e escreva o nome completo.

Lendo de um banco e gravando em outro

// Copia clientes ativos do ERP para o Joomla
DbTransactionHelper::run(function () {                       // transação no Joomla
    ClienteErpModel::query()
        ->where('ativo', true)
        ->chunk(500, function ($lote) {                      // leitura no ERP
            foreach ($lote as $clienteErp) {
                OrmTables::table('#__loja_clientes')->updateOrCreate(
                    ['documento' => $clienteErp->documento],
                    ['nome' => $clienteErp->nome]
                );
            }
        });
});

A leitura no ERP não precisa de transação. A gravação no Joomla fica toda numa transação só.

Transações em várias conexões

Cada conexão tem a sua própria transação, controlada separadamente:

DbTransactionHelper::run(function () {
    DbTransactionHelper::depth();          // 1: Joomla
    DbTransactionHelper::depth('erp');     // 0: ERP sem transação

    DbTransactionHelper::run(function () {
        DbTransactionHelper::depth('erp'); // 1: transação própria no ERP, não um savepoint
    }, ['connection' => 'erp']);           // COMMIT no ERP aqui
});                                        // COMMIT no Joomla aqui

lockForUpdate() exige transação na conexão da consulta. Travar uma linha do ERP dentro de uma transação que só existe no Joomla lança LogicException.

Gravando nos dois bancos: o limite importante

Não existe transação que cubra dois bancos. Cada run() confirma só a sua conexão. Se um banco confirmar e o outro falhar depois, o primeiro não é desfeito.

Não há como eliminar esse risco, mas dá para reduzi-lo bastante com este padrão:

  1. Transação principal por fora. Ela faz primeiro tudo o que pode falhar por regra de negócio.

  2. O outro banco por último, numa transação própria aninhada. Se ele falhar, a exceção sobe e a principal é desfeita: nenhum dos dois muda.

  3. Gravação idempotente no outro banco. Sobra uma janela pequena: o outro banco confirmou e o COMMIT da principal falha logo depois. Se a gravação puder ser repetida sem duplicar (índice UNIQUE + firstOrCreate), basta executar a operação de novo.

Padrão recomendado
public static function faturarPedido($pedidoId)
{
    return DbTransactionHelper::run(function () use ($pedidoId) {          // 1. Joomla
        $pedido = PedidoModel::query()
            ->where('id', (int) $pedidoId)
            ->lockForUpdate()
            ->first();

        if ($pedido === null || $pedido->status !== 'aberto') {
            throw new RuntimeException('Pedido inexistente ou já faturado.');
        }

        PedidoModel::query()->update($pedido->id, ['status' => 'pago']);

        return DbTransactionHelper::run(function () use ($pedido) {         // 2. ERP por último
            return TituloErpModel::query()->firstOrCreate(                  // 3. idempotente
                ['pedido_id' => $pedido->id],                               //    (pedido_id é UNIQUE)
                ['valor' => $pedido->total]
            );
        }, ['connection' => 'erp']);
    });
}
Se falhar…Resultado
a validação do pedidoNada muda em nenhum banco.
a gravação no ERPO ERP desfaz a sua parte; a exceção sobe e o Joomla também desfaz. Nada muda.
o COMMIT do Joomla, depois do ERP confirmarO título existe no ERP, mas o pedido continua "aberto". Executar de novo só marca o pedido, porque o firstOrCreate não duplica o título.

Para fluxos críticos com muito volume, considere uma fila: grave no Joomla a intenção ("faturar pedido 10") na mesma transação do pedido, e um job separado aplica no ERP e marca como concluído.

Conexões e desempenho

  • A conexão só abre na primeira consulta. Registrar e não usar não custa nada.
  • A mesma conexão é reaproveitada no request inteiro.
  • Em scripts longos (CLI, jobs), feche conexões que não vai mais usar com DbConnectionHelper::forget('erp').
