PermissionHelper

Permissões do Joomla (ACL) em uma linha no controller: core.edit no componente ou no registro, "só o dono do pedido", grupos e níveis de acesso, com resposta 401/403 padronizada e registro das tentativas negadas.

Visão geral

controller.php
public function excluir()
{
    // Token CSRF (campo, cabeçalho X-CSRF-Token ou JSON) e permissão; se faltar, responde 403/401
    if (!PermissionHelper::requireToken() || !PermissionHelper::require('core.delete')) {
        return;
    }

    $id = InputHelper::int('id');

    // O pedido é deste cliente? (protege contra IDOR: trocar o id na URL)
    if (!PermissionHelper::requireAccessEntity('pedido', $id, 'core.delete')) {
        return;
    }

    // ... exclui
}
  • Usa a ACL do Joomla ($user->authorise()): o que o administrador configura em Opções → Permissões do componente vale aqui.
  • Nunca lança exceção para negar: os métodos can* devolvem false em qualquer erro (falha fechada).
  • Respostas padronizadas: com o ApiResponseHelper carregado, nega com unauthorized() (401) ou forbidden() (403). Em JSON, responde e encerra; em HTML, mostra a mensagem do Joomla.
  • Registra as negativas: log permission_helper.warning com usuário, grupos, IP e URL e, se o AuditHelper estiver carregado, um evento de segurança no banco.

Os métodos require* devolvem false quando negam. Em requisições HTML o Joomla não encerra: sempre use if (!PermissionHelper::require(...)) { return; }.

Ações e assets do Joomla

Uma permissão é uma ação num asset. As ações padrão são core.admin, core.manage, core.create, core.edit, core.edit.own, core.edit.state, core.delete; o componente pode declarar outras no access.xml (ex.: loja.pedido.faturar). O asset é o componente (com_loja) ou um registro (com_loja.pedido.15).

administrator/components/com_loja/access.xml
<access component="com_loja">
    <section name="component">
        <action name="core.admin" title="JACTION_ADMIN" />
        <action name="core.manage" title="JACTION_MANAGE" />
        <action name="core.create" title="JACTION_CREATE" />
        <action name="core.edit" title="JACTION_EDIT" />
        <action name="core.delete" title="JACTION_DELETE" />
        <action name="loja.pedido.faturar" title="Faturar pedidos" />
    </section>
</access>

Sem componente informado, vale o option da requisição (com_loja), ou o definido em setDefaultComponent().

Token CSRF: requireToken()

Toda task que grava precisa conferir o token do Joomla. O JSession::checkToken() do Joomla 3 só conhece o campo do formulário; requisições JSON (Vigia.js com json: true, fetch) mandam o token no cabeçalho X-CSRF-Token. O requireToken() aceita os três formatos nas três versões do Joomla:

FormatoQuem manda
campo <token>=1 no POSTJHtml::_('form.token'), Vigia.js (multipart), formulários clássicos
cabeçalho X-CSRF-Token: <token>Vigia.js, fetch/axios com Joomla.getOptions('csrf.token')
JSON {"<token>": 1}Vigia.http com json: true
public function salvar()
{
    try {
        if (!PermissionHelper::requireToken()) {
            return;   // 403 "Sua sessão expirou. Recarregue a página e tente novamente." + log
        }

        if (!PermissionHelper::require('core.edit')) {
            return;
        }

        // ...
    } catch (Throwable $e) {
        return ApiResponseHelper::exception($e);
    }
}

requireToken() / hasValidToken()estático

PermissionHelper::requireToken(string $message = '...', string $method = 'post', string|null $redirect = null): bool PermissionHelper::hasValidToken(string $method = 'post'): bool

$method: onde procurar o campo (post, get ou request); cabeçalho e JSON valem sempre. A comparação do cabeçalho é em tempo constante. Requisições GET não devem alterar nada: não as proteja com token, use POST.

Para expor o token ao JavaScript sem formulário: JFactory::getDocument()->addScriptOptions('csrf.token', JSession::getFormToken()); (o Joomla 4/5 já faz isso no administrador). O Vigia.js lê Joomla.getOptions('csrf.token') sozinho.

Consultar sem responder: can*

Devolvem true/false. Use em views (mostrar ou esconder botões) e em regras de negócio.

MétodoVerdadeiro quando
can($acao, $asset = null, $usuario = null)o usuário logado tem a ação no asset (padrão: o componente atual)
canComponent($acao, $componente = null)tem a ação no componente
canEntity($acao, $tipo, $id, $componente = null)tem a ação no registro (asset com_loja.pedido.15)
canAny(array $acoes, $asset) / canAll(...)tem alguma / todas
isAdmin($componente = null)core.admin no componente ou no site (Super Usuário)
isManager($componente = null)core.manage ou admin
canAccessEntity($tipo, $id, $acao = 'core.view')admin, ou ACL do registro, ou o resolvedor do tipo diz que sim
evaluate(callable $regra, $usuario, $contexto)a função ($usuario, $contexto) devolve verdadeiro
tmpl/default.php
<?php if (PermissionHelper::can('core.edit')) : ?>
    <a class="btn btn-primary" href="<?php echo JRoute::_('index.php?option=com_loja&task=pedido.edit&id=' . (int) $pedido->id); ?>">Editar</a>
<?php endif; ?>

<?php if (PermissionHelper::canEntity('loja.pedido.faturar', 'pedido', $pedido->id)) : ?>
    <button type="button" data-faturar="<?php echo (int) $pedido->id; ?>">Faturar</button>
<?php endif; ?>

Esconder o botão não protege nada: a task do controller precisa do require* correspondente.

Exigir no controller: require*

Mesmos critérios dos can*; se negar, registra, responde 401/403 e devolve false. Sem login, todos respondem 401 antes de olhar a permissão.

MétodoDevolve se permitido
requireLogin($mensagem, $redirect)o JUser
require($acao, $asset, $mensagem, $redirect, $contexto)true
requireComponent($acao, $componente, ...)true
requireEntity($acao, $tipo, $id, $componente, ...)true
requireAccessEntity($tipo, $id, $acao = 'core.view', ...)true
requireAny(array $acoes, ...) / requireAll(...)true
requireGroup($grupoId, ...) / requireAnyGroup(array $grupos, ...)true
requireUserIn($ids, ...) / requireAllowedUser(array $ids, ...)true
requireCallback(callable $regra, ...)true
// Mensagem e destino próprios (o destino só vale em requisições HTML)
if (!PermissionHelper::require('loja.pedido.faturar', null, 'Só o financeiro fatura pedidos.', JRoute::_('index.php?option=com_loja&view=pedidos', false))) {
    return;
}

// Regra de negócio como permissão
if (!PermissionHelper::requireCallback(function ($usuario) use ($pedido) {
    return $pedido->status === 'aberto' && (int) $pedido->vendedor_id === (int) $usuario->id;
}, 'Só o vendedor do pedido pode alterá-lo enquanto estiver aberto.')) {
    return;
}

Acesso por registro: resolvedores (contra IDOR)

A ACL do Joomla responde "pode editar pedidos", não "pode editar este pedido". Para a área do cliente ("só vejo os meus pedidos"), registre um resolvedor por tipo. canAccessEntity/requireAccessEntity liberam se o usuário for admin do componente, se a ACL do registro permitir, ou se o resolvedor devolver true.

// Uma vez, no início do componente (ex.: site/loja.php)
PermissionHelper::registerEntityResolver('pedido', function ($pedidoId, $usuario, $contexto) {
    return OrmTables::table('#__loja_pedidos')
        ->where('id', (int) $pedidoId)
        ->where('cliente_user_id', (int) $usuario->id)
        ->exists();
});

PermissionHelper::registerEntityResolver('endereco', function ($id, $usuario) {
    return OrmTables::table('#__loja_enderecos')->where('id', (int) $id)->where('user_id', (int) $usuario->id)->exists();
});

// No controller
$id = InputHelper::int('id');

if (!PermissionHelper::requireAccessEntity('pedido', $id)) {
    return;   // 403 "Você não possui permissão para acessar este registro." + log + auditoria
}

O $contexto recebe entity_type, entity_id, component, action e o que você passar no último argumento. Tipos aceitam letras, números, _ e -; ids vazios, zero ou negativos são recusados.

Usuário, grupos e níveis de acesso

MétodoDevolve
user($usuario = null)o JUser informado ou o logado
userId(), isLoggedIn(), isGuest()id (0 = visitante) e atalhos
groups()ids dos grupos autorizados (inclui os herdados)
hasGroup($id), hasAnyGroup(array), hasAllGroups(array)bool
viewLevels(), canView($nivel)níveis de acesso (o campo access dos registros)
isUserIn($ids), allowsUser($userId, array $ids)o usuário está numa lista fixa de ids
// Lista só o que o nível de acesso do usuário permite (como o com_content faz)
$niveis = PermissionHelper::viewLevels() ?: array(1);   // 1 = Público
$artigos = OrmTables::table('#__loja_paginas')->whereIn('access', $niveis)->get();

Prefira ações (can('loja.pedido.faturar')) a grupos fixos (hasGroup(9)): o id do grupo muda de um site para outro, e a ação pode ser concedida a qualquer grupo pelo administrador.
